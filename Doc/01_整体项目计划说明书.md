## 1. 项目定义与交付目标

构建一个可实机演示的涂层质检工位原型：操作员录入工件编号，按指定点位使用测厚仪测量；Linux 接收测量值、管理检测任务、判断结果、保存记录并上传云端；STM32F4 读取现场输入、管理现场状态、输出结果指示，并在 Linux 失联时撤销合格输出。

项目角色为独立开发。质量规则属于演示配置，实际生产使用还需要工艺依据与仪器校准证据。首版的普通输出通过 LED 演示，不能据此声称实现了经过认证的工业安全控制。

最终交付必须包含：真实仪器演示、Ubuntu 与 STM32 实机联调、OneNET 上报、异常测试记录、源代码、协议说明和演示视频。ARM 移植作为后续阶段单独验收。

## 4. 两侧责任边界

### Linux：五项核心工作

| 工作 | 实现重点 | 交付证据 |
|---|---|---|
| 1. 接入测厚仪 | 复用 BlueZ 库；通知解析、CRC、重连、连接代次 | 原始通知和有效测量日志 |
| 2. 建立检测任务 | 工件编号输入、产品规则、唯一 inspection_id | 可查询的任务与规则快照 |
| 3. 管理多点检测和判定 | 单线程拥有业务状态；点位开启、采集、人工确认 | 点位记录、PASS/FAIL/ABORTED 场景 |
| 4. 与 MCU 通信 | 主站轮询、完整命令块、序号与确认、应用心跳 | 双侧对应的协议日志 |
| 5. 保存和上传记录 | 逐点落库；最终判定与 Outbox 同事务；OneNET 回复确认 | 本地记录、云端事件、补传记录 |

部署、日志、配置和优雅退出是支撑上述五项工作的工程要求。

### MCU：五项核心工作

| 工作 | 实现重点 | 交付证据 |
|---|---|---|
| 1. 读取现场输入、控制输出 | 去抖、输入事件保持、输出默认关闭 | 开关/按钮与灯具实物演示 |
| 2. RS485/Modbus RTU 从站 | DMA、缓冲、RTU 定界、CRC、03/04/06/10 功能码 | Ubuntu 主站读写实机 |
| 3. 管理现场状态机 | 状态合法性、任务 token 匹配、命令幂等 | 正常和非法命令测试 |
| 4. 实现失联保护 | 变化的应用心跳；超时撤销 PASS | 断串口、杀进程、业务线程停滞测试 |
| 5. 健康检查与看门狗 | 关键任务报告进度；满足条件才喂 IWDG | 任务停滞、复位与输出测试 |

厚度测量来自仪器；质量判定属于 Linux。MCU 不复制质量规则，也不自行生成检测结果。

## 5. 首版范围

首版实现单工位、单仪器、单个活动检测任务。工件身份由命令行录入，可兼容作为键盘输入的 USB 条码枪。测量点数配置为 1～5，演示产品先选 5 点；后续再扩大点数与云端数据模型。

工位界面使用终端提示和现场按钮。产品规则固定为基材模式约束、厚度上下限和全部点通过。上下限包含边界；中止与系统故障不记为质量 FAIL。

ARM 移植、复杂 Web/Qt、多工位、OTA、自研内核驱动与完整云端业务后台属于后续工作。

## 6. 统一检测流程

1. 两侧启动，输出关闭。Linux 建立 Modbus 连接并执行 SYNC_SAFE，操作员确认复位。
2. 到位开关有效，MCU 进入 READY；Linux 读取状态并录入工件编号、产品型号。
3. Linux 创建任务并保存规则快照。START 命令被 MCU 确认后，两侧进入检测中。
4. 对每个点执行“开启采集窗口→产生新测量→终端显示候选值→操作员确认”。
5. 已确认点写入 SQLite，提交成功后才显示“该点已保存”。
6. 点数满足要求后，Linux 判定并在同一事务内写入最终结果和 Outbox。
7. Linux 发送 APPLY_RESULT。MCU 核对 host_epoch、session_token 和状态，输出 PASS/FAIL 并确认。
8. Linux 另行保存现场执行状态；上传线程独立上报检测结果。
9. 工件离开，MCU 清除结果灯和活动 token。下一工件使用新的任务编号与 token。

数据库中的质量结果和现场执行状态分开：已判定 PASS 并不代表 MCU 已显示或执行成功。云端检测事件表达质量结果，不宣称现场已经放行。

## 7. 点位真实性与数据归属

现有仪器协议没有充分证据提供唯一测量序号、工件 ID 或空间点位 ID。系统只能根据人工操作流程建立归属，不能把连续五条通知直接当成五个空间点位。

开发前录制实机通知，验证一次探头测量是否产生多条报文、重新连接是否重发旧值、相同厚度是否正常重复出现。

每个采集窗口包含 inspection_id、point_index、开启时的单调时钟和 BLE connection_generation。只接受同一连接代次、窗口开启后收到的数据；重连后中止当前任务，重新开始。人工确认前收到的多条通知不自动累计成多个点。

系统记录的是本机接收时间；未经验证，不将其描述为仪器内部测量时间。网关事件编号也不等于仪器原生测量编号。厚度值相等不能作为删除重复测量的依据。

## 8. 两侧状态设计

| Linux 状态 | 含义 |
|---|---|
| IDLE | 等待工件 |
| READY | 工件、身份、规则、仪器和 MCU 已准备 |
| INSPECTING | 管理点位采集与确认 |
| FINALIZING | 完成判定及数据库事务 |
| COMPLETED | 质量结果已提交，现场执行状态另行记录 |
| ABORTED | 当前任务未完成，中止原因已保存 |
| FAULT | 系统故障阻止新任务 |

| 寄存器值 | MCU 状态 | 含义 |
|---|---|---|
| 0 | BOOT | 初始化，输出关闭 |
| 1 | IDLE | 无工件，已完成同步且健康 |
| 2 | READY | 工件到位，等待合法 START |
| 3 | INSPECTING | 绑定活动 session_token，等待结果 |
| 4 | COMPLETED | 已接受 PASS 或 FAIL |
| 5 | FAULT | 输出撤销，等待健康恢复及复位 |

质量结果另设 PASS/FAIL；故障不能伪装成 FAIL。BLE 中断、工件中途离开、业务队列溢出或数据库失败均中止任务。恢复后重新录入/确认工件并新建任务。

## 9. 通信协议：三份文档的共同约定

### 9.1 基本参数

首版：Linux 主站、MCU 从站，地址 1，115200、8E1。若硬件或协议库不支持该配置，联调前统一修改配置与两侧文档。

支持 04 读取输入寄存器、03 读取保持寄存器、06 写心跳、10 写命令块；其他功能返回标准异常响应。RTU 寄存器和多寄存器高低字顺序统一，32 位值高字在低地址。

USART IDLE 只协助取走新增数据；RTU 帧边界按 t1.5/t3.5 定时处理。115200 下按官方指南建议的固定时间实现并验证。发送后等待 USART 真正发送完成再撤销 DE。

### 9.2 输入寄存器快照

| 地址 | 内容 |
|---|---|
| 0x0000 | MCU_STATE |
| 0x0001 | INPUT_FLAGS：bit0 到位，bit1 ACTION，bit2 RESET |
| 0x0002 | OUTPUT_FLAGS：bit0 绿灯，bit1 红灯，bit2 黄灯 |
| 0x0003 | FAULT_CODE |
| 0x0004 | HEALTH_MASK |
| 0x0005 | MCU_HEARTBEAT |
| 0x0006～0x0007 | UPTIME_MS，高字/低字 |
| 0x0008～0x0009 | ACTIVE_SESSION_TOKEN，高字/低字 |
| 0x000A～0x000B | ACK_CMD_SEQ，高字/低字 |
| 0x000C | ACK_STATUS |
| 0x000D～0x000E | INPUT_EVENT_SEQ，高字/低字 |
| 0x000F | INPUT_EVENT_CODE：1 ACTION，2 RESET |
| 0x0010 | RESET_REASON |
| 0x0011～0x0012 | COMM_ERROR_COUNT，高字/低字 |
| 0x0013 | PROTOCOL_VERSION，首版为 0x0200 |
| 0x0014～0x0015 | ACK_HOST_EPOCH，高字/低字 |

一次读请求返回一致快照。按钮事件保持到主站确认，首版只允许一个待确认按钮事件；等待期间的新按键明确计入拒绝/忙碌诊断，不覆盖旧事件。

### 9.3 心跳与命令块

0x0100 为 HOST_HEARTBEAT，通过 06 写入变化的 16 位计数。相同值重复写入不刷新健康时间。Linux 业务线程健康时，通信线程才继续发送新的计数。

命令通过 10 一次写入 0x0110～0x0118，共 9 个寄存器：

| 地址 | 内容 |
|---|---|
| 0x0110～0x0111 | HOST_EPOCH，高字/低字 |
| 0x0112～0x0113 | SESSION_TOKEN，高字/低字 |
| 0x0114～0x0115 | CMD_SEQ，高字/低字 |
| 0x0116 | OPCODE |
| 0x0117～0x0118 | ARG，高字/低字 |

HOST_EPOCH 标识一次主站运行/重新同步周期。session_token 为 MCU 使用的非零 32 位任务标识，与 Linux inspection_id 持久化关联。同一 epoch 内 CMD_SEQ 单调增加，回绕前重新同步。Linux 同时只发送一个待确认业务命令。

| OPCODE | 命令 | 条件/作用 |
|---|---|---|
| 1 | SYNC_SAFE | 建立新 epoch；撤销输出、清除旧 token 和旧待确认按钮事件，进入 FAULT 待人工复位 |
| 2 | START | READY、到位且健康；绑定新 token，进入 INSPECTING |
| 3 | APPLY_RESULT | INSPECTING 且 token 匹配；ARG=1 PASS，ARG=2 FAIL |
| 4 | ACK_INPUT_EVENT | ARG 为待确认按钮事件序号 |
| 5 | RESET_FAULT | 心跳、任务健康及 IO 条件恢复后，回到 IDLE/READY |
| 6 | ABORT | 中止当前任务并撤销输出，进入 FAULT |

ACK_STATUS：0 无确认，1 已执行，2 状态拒绝，3 token 拒绝，4 epoch/序号拒绝，5 健康条件拒绝，6 参数/命令拒绝。

相同 epoch、序号和完整命令的重传返回既有处理结果，不再次执行。相同序号但不同内容必须拒绝。Modbus 写响应只代表协议处理，Linux 还要读取 ACK_HOST_EPOCH、ACK_CMD_SEQ、ACK_STATUS、MCU_STATE 和 token 确认业务执行，避免重启前同序号的旧确认被误认。

### 9.4 初始时间参数

计划值：主站轮询 100 ms，应用心跳 200 ms，MCU 心跳超时 1500 ms。串口单次事务超时和重试次数在实测后确定，所有重试必须有次数/时间上限。

1500 ms 是初始配置，最终保护时间包含检测任务调度与输出刷新延迟，应以实际测量值报告。

## 10. 存储与云端上传约定

本地保存 inspection、measurement、outbox、actuation_log 四类数据。规则快照存入任务，允许同一工件复检，但每次使用新 inspection_id。

任务创建、点位确认、最终完成分别使用短事务。最终完成事务必须同时写入 PASS/FAIL 与待上传事件；数据库写失败时不发送 PASS。

云端首选 OneNET 物模型事件 InspectionCompleted；状态属性用于设备在线/工位状态。完整点位与原始诊断以本地记录为准，首版云端事件包含业务编号、工件编号、产品、规则版本、结果、1～5 个确认测量值及时间信息。字段按平台物模型验证后冻结。

上传队列状态：PENDING → WAIT_REPLY → PLATFORM_ACCEPTED；超时回到 RETRY_WAIT。平台明确拒绝进入 REJECTED 并记录原因。进程重启后，未获得确认的事件重新待传。

三个 ID 分别使用：inspection_id 是检测任务编号；event_id 是稳定的业务事件编号；request_id 是 OneNET 请求/回复关联编号。重试保留 event_id，不能用平台物模型事件名称替代业务唯一编号。

首版承诺本地可恢复、失败重试、平台接受确认。OneNET 是否自动按业务 event_id 去重没有得到验证，不能宣称云端业务 exactly-once。若后续加入追溯后台，再实现 event_id 唯一入库与业务确认。

## 11. 异常策略

| 情况 | Linux 行为 | MCU 行为 |
|---|---|---|
| BLE 断开 | 保存已确认点，中止任务；重连后新任务 | 收到 ABORT 撤销输出 |
| 工件测量中离开 | 中止任务，禁止继续归属测量 | 立即撤销输出并报故障 |
| Linux 崩溃/串口断开 | 重启后不恢复旧 PASS | 心跳超时，撤销输出 |
| 业务线程卡住而通信线程仍在 | 停止推进应用心跳 | 心跳超时 |
| MCU 复位 | 检查状态/token，当前任务中止，重新同步 | 输出关闭，旧 token 无效 |
| 数据库失败/空间不足 | 中止，禁止开始新任务；报告错误 | ABORT 或心跳超时进入故障 |
| MQTT/互联网中断 | 本地检测继续，事件待传 | 正常执行本地流程 |
| OneNET 拒绝上报 | 保留事件，展示原因，按可恢复错误处理 | 不影响已完成本地检测 |

正常退出先禁止新任务、保存中止记录并请求撤销现场输出，再停止采集与通信线程。强制退出由 MCU 心跳保护兜底。

## 12. 分阶段实施与验收

| 阶段 | 工作 | 进入下一阶段的条件 |
|---|---|---|
| P0：冻结接口与验证设备 | 实机 BLE 行为；F4 型号/引脚；RS485 参数；OneNET 账号、事件与回复验证 | 原始采样记录和一条成功上报；接口清楚 |

| P3：两侧联调 | epoch/token/seq/ACK、按钮事件、异常中止 | 真实仪器＋真实 RS485 完成全流程 |
| P4：上传与补传 | Outbox、OneNET、回复关联、重试 | 断网后记录仍可查询，恢复后全部获得平台回复或明确失败 |

## 13. 必测场景与证据

- 正常 PASS、任一点超界 FAIL、材料模式不匹配、规则上下限边界。
- 相同厚度的不同点、连续多条通知、采集窗口外数据、BLE 重连。
- 重复 START/APPLY_RESULT、旧 token、旧 epoch、参数错误、按钮短按。
- 最终事务前后崩溃、事务成功但命令未确认、平台接受后本地尚未更新时崩溃。
- 断网、断 RS485、杀 Linux、停业务线程、MCU 复位、数据库不可写。
- 分别区分进程退出与整机断电；检查数据库、任务与输出，不能只检查服务是否重启。

记录真实测量次数、仿真次数、故障注入次数及24h负载，分别报告。测量保护延迟、恢复耗时、待传积压及本地记录一致性，不预填“零丢失”或“无重复”成果。
