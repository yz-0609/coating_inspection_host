## 1. 先认识对象的四种角色

### 1.1 不要把“类”“对象”“线程”当成同一件事

看见 `InspectionWorker` 时，先分别回答三个问题：

- `InspectionWorker` 是一个**类型定义**，规定有哪些变量和函数。
- `worker` 是这个类型的**具体对象**，有自己的任务、候选、状态。
- `worker.start()` 创建一条**执行线程**，在其中调用该对象的 `run()`。

对象用于保存状态，线程负责执行代码。对象不一定拥有线程，拥有线程的对象也不是所有函数都在那条线程执行。

例如 `worker.start()` 由主线程调用；`worker.run()` 在新建的业务线程执行；`worker.request_stop()` 通常由主线程调用。因此要逐个函数判断执行位置。

### 1.2 四种角色的工程意义

| 角色 | 项目例子 | 阅读重点 |
|---|---|---|
| 数据对象 | `Task`、`Point`、`Measurement`、`Event` | 每个字段代表什么，何时有效，数据是副本还是借用 |
| 抽象接口 | `IClock`、`IInstrument`、`IWorkstation`、`Transport` | 调用方能要求什么，返回值承诺什么 |
| 执行或协调对象 | `InspectionWorker`、`ReplayInstrument`、`WorkstationWorker` | 在哪个线程修改状态，怎样调度、怎样停止 |
| 资源封装 | `InspectionRepository`、`Statement`、`Transaction` | 谁申请资源，谁释放，异常后怎样收尾 |

有些类同时具有两种角色。例如 `ModbusTransport` 实现传输行为，也负责释放串口句柄。

`struct` 在 C++ 中也可以有函数；此工程常用 `struct` 表达公开的数据集合。不能只根据 `class`/`struct` 关键字判断对象是否会执行逻辑，要看实际成员。

### 1.3 每读一个类，都使用这张卡片

```text
1. 职责：这个对象解决什么具体问题？
2. 创建：谁创建它，构造函数现在就做 I/O 吗？
3. 所有权：谁负责销毁它，它借用了谁？
4. 线程：哪些函数在哪个线程执行？
5. 状态：哪些变量会变化，谁可以修改？
6. 入口：别人通过什么函数与它协作？
7. 失败：false、异常、超时分别表示什么？
8. 收尾：对象销毁前，线程和资源怎样停止？
```

本文每节都围绕这些问题展开。知道某个变量的中文翻译，还不等于理解了它：你需要找到写入它的地方，再找到读取它的判断。

## 2. main 中的对象组装：从实例建立关系

源码：[main.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/app/main.cpp)。重点先读创建共享对象到启动线程的部分，再读退出部分。

### 2.1 这几行是整个工程的对象入口

源码节选：

```cpp
SystemClock clock;
BoundedQueue<Event> queue(cfg.queue_capacity);
BusinessHealth health;
CandidateDisplay display;

auto sink = [&](Event e) {
    if (e.kind == EventKind::Snapshot)
        e.bound_candidate = display.current();
    return queue.push(std::move(e));
};

auto instrument = make_instrument(cfg, clock, sink);
auto workstation = make_workstation(cfg, clock, health, sink);
InspectionWorker worker(cfg, clock, queue, health, display,
                        *instrument, *workstation);
```

逐句读出工程关系：

| 代码对象 | main 持有什么 | 后续谁会用到 |
|---|---|---|
| `clock` | 一个真实时钟对象 | 业务、仪器、工位读取时间 |
| `queue` | 一个事件队列 | 多个生产者投递，业务线程消费 |
| `health` | 共享原子健康信息 | 业务更新，工位读取，退出时 main 禁用 |
| `display` | 当前展示的候选编号与锁 | 业务发布/清除，工位投递快照时读取 |
| `sink` | 一个可调用的 lambda 对象 | 统一封装事件入队规则 |
| `instrument` | `unique_ptr<IInstrument>` | main 控制生命周期，业务只使用接口 |
| `workstation` | `unique_ptr<IWorkstation>` | main 控制生命周期，业务提交命令 |
| `worker` | 一个业务协调对象 | 内部启动业务线程，持有当前任务和仓库 |

`*instrument` 取出智能指针指向的对象，传给构造函数的引用参数。**这不会把仪器的所有权转移给 worker。** 仪器仍由 main 中的智能指针拥有。

### 2.2 构造函数通常只是“准备对象”，start 才开始持续运行

主要启动顺序是：

```cpp
worker.start();
instrument->start();
workstation->start();
```

先启动业务消费者，再启动设备生产者。之后 main 单独创建执行 `cli_loop()` 的输入线程。

这里的“先启动”不表示业务线程中的初始化已全部完成。`start()` 返回只意味着线程已经创建，线程调度和初始化继续异步进行。后续操作仍需满足状态机检查。

同样，“构造不启动线程”不等于“构造完全没有工作”：`ReplayInstrument` 构造时会读取并解析回放文件；`MockTransport` 构造时会设置初始状态；数据库则在业务线程的 `run()` 内打开。

### 2.3 应用明确创建的执行角色

| 执行角色 | 执行入口 | 主要责任 |
|---|---|---|
| 主线程 | `main()` | 组装、启动、观察退出、按顺序停止 |
| 业务线程 | `InspectionWorker::run()` | 独占任务状态和 SQLite 连接 |
| 仪器线程 | `ReplayInstrument::run()` 或 `BluezReader::run()` | 采集/回放并投递测量 |
| 工位线程 | `WorkstationWorker::run()` | 独占传输对象，轮询、心跳、命令确认 |
| 输入线程 | `cli_loop()` | 拼接完整命令行并投递事件 |

BLE 与回放按配置选择其中一个后端。应用没有独立数据库线程，也没有云上传线程。GLib 等库可能创建内部辅助线程，因此操作系统显示的线程数不一定恰好是五个。

### 2.4 为什么退出顺序也是对象设计的一部分

正常路径先请求业务停止并 `join()`，此时设备线程仍在运行，业务可以收到 ABORT 等命令的反馈。之后停止仪器、工位和输入线程，最后关闭事件队列、管道。

这满足两个实际条件：

1. 业务收尾时，通信对象还存在、还能工作。
2. 通信回调结束后，队列和 `display` 才可以销毁。

引用与 `[&]` 捕获都不会延长被引用对象的寿命。**这些对象活得足够久，靠的是创建、停止、销毁顺序。**

本节自查：看到 `worker` 构造参数中的 `*workstation`，你应该想到“借用工位接口”，而不是“复制一个工位线程”。

## 3. 数据对象：先读懂业务代码操作的内容

源码：[config.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/config.hpp)、[types.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/types.hpp)、[events.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/events.hpp)。

### 3.1 Config：一份经过启动校验的参数集合

**职责：** 把设备选择、超时、数据库、产品规则等参数集中表达出来。

它不是配置管理线程，也不会自己监视文件变化。main 调用 [load_config()](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/support/config.cpp)，得到 `Config` 值，再把它传给各模块。

| 字段组 | 主要成员 | 谁读取、影响什么 |
|---|---|---|
| 身份 | `station_id`、`device_name` | 结果追溯、蓝牙匹配、测量仪器身份 |
| 仪器后端 | `instrument_type`、`replay_file` | 工厂选择 BLE/回放，回放读取文件 |
| 工位后端 | `workstation_type`、`serial_device` | 选择 Mock/Modbus、打开哪个串口 |
| 通信 | `baudrate`、`slave_id`、`response_ms` | 串口参数、单次响应等待 |
| 调度 | `poll_ms`、`heartbeat_ms`、`health_ms` | 轮询、发变化心跳、健康戳有效期 |
| 命令 | `command_ms`、`retries` | 待确认命令总期限和重发次数 |
| 采集 | `measurement_ms` | 每个点的采集与确认总窗口 |
| 存储 | `database_path`、`database_busy_ms`、`disk_min_mb` | DB 位置、锁等待、最低可用空间 |
| 缓冲 | `queue_capacity` | 公共事件队列容量 |
| 演示/诊断 | `replay_loop`、`replay_interval_ms`、`allow_test_controls`、`raw_notifications` | 回放时序、测试控制、原始字节日志 |
| 质量与云 | `rules`、`cloud_adapter` | 按产品查规则；当前云只允许 disabled |

重要默认值：轮询 100 ms、心跳 200 ms、业务健康 500 ms、单次响应 150 ms、命令总期限 1000 ms、额外重试 2 次、点位窗口 30000 ms、事件队列 128 条。配置可以改变这些值。

`load_config()` 不只是给字段赋值，还会检查后端名称、时间关系、材料、点数、阈值。数据库与回放的相对路径以**配置文件目录**为基准解析。

工程认识：`Config` 在启动后按配置快照使用，各对象有自己的值副本；类型本身不是 `const`，所以“运行期间不修改”是当前使用方式，而不是所有字段都有编译器强制保护。

### 3.2 Rule：一次检测必须依据的质量规则

| 成员 | 含义 | 为什么需要保存 |
|---|---|---|
| `product_id` | 产品型号 | 知道哪一种产品 |
| `version` | 规则版本 | 日后知道按哪版规则判断 |
| `substrate` | FE 或 NFE | 每个确认点的材料必须匹配 |
| `required_points` | 1～5 个确认点 | 防止少测或多测 |
| `min_milli_um`、`max_milli_um` | 含边界的上下限 | 精确比较厚度 |

`milli_um` 是**千分之一微米**：`150000` 表示 `150 μm`，不是 150000 μm，也不是 150 mm。

`begin()` 把配置里的 Rule **复制进 Task**，仓库再保存完整规则 JSON。因此历史任务可以保留当次判定依据，而不依赖以后配置文件的内容。

关联函数 `passes(rule, points)` 位于 [runtime.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/support/runtime.cpp)：点数必须恰好相等，每一点材料匹配、厚度落在上下限内，才能 PASS。它不取平均值。

### 3.3 inspection::Measurement：一条待归属、待确认的测量

| 成员 | 保存什么 | 在业务里怎样用 |
|---|---|---|
| `candidate_id` | 本机生成的候选 UUID | 明确选择某一条测量 |
| `instrument_id` | 配置中的仪器标识 | 追溯来源 |
| `substrate` | 归一化材料字符串 | 过滤未知材料、最终质量比较 |
| `group` | 仪器携带的组名 | 追溯与诊断，不是物理测点坐标 |
| `thickness_milli_um` | 精确整数厚度 | 入库、阈值比较 |
| `wall_ms` | 通知接收的日历时间 | 历史记录 |
| `mono_ms` | 通知接收的单调时间 | 是否晚于窗口开始 |
| `generation` | 仪器连接代次 | 防止旧连接数据混入新窗口 |
| `local_sequence` | 本次采集对象的诊断序号 | 观察接收顺序，不做厚度去重 |

接到 Measurement 不等于已经得到正式检测点。它还需要通过窗口检查，并由操作员指定候选确认。

两个厚度都是 150 μm 的测量，仍可能是两次独立测量。代码按候选身份处理，不按数值合并。

注意另一个同名类型 `thickness::Measurement`：它只是厂商协议解码结果，没有任务和候选身份。二者的转换在 `InstrumentEvents::measurement()`，第 11 章详解。

### 3.4 Point：一条已经选定并准备保存的确认点

源码节选：

```cpp
struct Point {
    int index = 0;
    Measurement value;
    std::int64_t confirmed_ms = 0;
};
```

`index` 从 1 开始；`value` 是 Measurement 值成员，保存选定测量的副本；`confirmed_ms` 记录确认时间。

创建局部 Point 并不自动证明保存成功。`confirm()` 先组装它，再调用 `save_point()`；数据库提交成功后，才追加到任务内存列表并输出成功日志。

`Point::value` 不是对当前最新候选的引用。后续出现新测量不会把已选定点的厚度改掉。

### 3.5 Task：一次检测的完整上下文

| 成员 | 含义 | 变化方式 |
|---|---|---|
| `id` | 一次检测的 UUID | 创建后保持不变；复检生成新 id |
| `workpiece` | 操作员输入的工件编号 | 同一工件可有多次检测 |
| `result` | 空、PASS、FAIL | 点数足够并完成质量判定后设置 |
| `state` | 持久化任务状态 | StartPending → Inspecting → Completed，或 Aborted |
| `rule` | 当次规则副本 | 从配置复制，不在测量过程中换规则 |
| `token` | MCU 使用的非零任务标识 | 从 SQLite 持久化计数器分配 |
| `started_ms` | 创建任务时的日历时间 | 当前实现不是 START ACK 返回时间 |
| `points` | 已确认点的内存列表 | 逐点追加，每点同时有数据库记录 |

不要把 `workpiece`、`Task::id`、`token` 当成同一个编号：它们分别表示工件身份、一次检测身份、现场协议任务身份。

业务中的 `std::optional<Task> task_` 表示“可能暂时没有任务”。`task_` 有值也不代表仍在检测：完成和中止后可能暂时保留该对象，直到后续处理释放它。

### 3.6 TaskState 和 InspectionPhase：两个状态维度

| 类型 | 回答的问题 | 例子 |
|---|---|---|
| `TaskState` | 这次检测在持久化层处于什么状态？ | INSPECTING、COMPLETED |
| `InspectionPhase` | 操作流程现在允许做哪一步？ | WaitArm、WaitConfirm |
| `McuState` | 现场 MCU 当前处于什么状态？ | Ready、Inspecting、Fault |

例如同一 TaskState::Inspecting 可以对应 WaitArm、WaitNewMeasurement、WaitConfirm。前者比较粗，后者表达更细的操作步骤。

三者没有自动联动机制。`InspectionWorker` 根据快照和命令反馈显式修改并检查它们。

### 3.7 Event：跨线程交接的一份自有数据

| `kind` | 应读取的主要字段 | 谁产生 |
|---|---|---|
| `InstrumentState` | `online`、`generation` | 仪器适配层 |
| `Measurement` | `measurement` | 仪器适配层 |
| `Snapshot` | `snapshot`、`bound_candidate` | 工位线程；sink 补编号 |
| `CommandDone` | `command`、`success`、`detail`、`snapshot` | 工位线程 |
| `Cli` | `text` | 输入线程 |
| `Stop` | 类型本身表达停止 | 业务分发支持此类型 |

Event 是普通结构体，不是 union。所有成员都存在，但约定按照 `kind` 解释有效字段。

默认 `kind` 是 Cli。因此生产者每次都要明确设置所需事件类型；不要只给 `measurement` 赋值却忘记类型。

它保存 string、Measurement、Snapshot 等值，不把 BLE 回调的临时指针塞进队列。这让回调返回后，业务线程仍能安全读取消息。

## 4. IClock、SystemClock、ManualClock：把“时间来源”变成依赖

源码：[support.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/support.hpp)、[runtime.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/support/runtime.cpp)。

### 4.1 IClock 定义能力，不提供具体时钟数据

源码节选：

```cpp
class IClock {
  public:
    virtual ~IClock() = default;
    virtual std::int64_t mono_ms() const = 0;
    virtual std::int64_t wall_ms() const = 0;
};
```

读成工程契约：“凡是时钟实现，必须能返回单调毫秒和日历毫秒；业务通过接口调用，不关心具体来源。”

`= 0` 表示接口要求实现这个函数，不表示函数返回数值 0。`virtual` 使通过 IClock 引用调用时，能够进入实际实现。

### 4.2 SystemClock 没有自己的线程，也不主动触发超时

它没有业务成员状态，关键函数只有两个：

| 函数 | 实现来源 | 实际用途 |
|---|---|---|
| `mono_ms()` | `std::chrono::steady_clock` | 窗口、健康有效期、命令期限 |
| `wall_ms()` | `std::chrono::system_clock` | 数据库时间和审计记录 |

`duration_cast<milliseconds>(...).count()` 把时钟原生时间转换为整数毫秒。

单调时间的绝对数值不要当日期，也不要用不同进程启动后的采集窗口上下文相互替代。它主要用于当前运行里的时间差。

代码 `clock_.mono_ms()` 在调用它的线程当场执行。SystemClock 不会另起线程去回答时间，也不负责“等 30 秒后调用 abort”。超时判断由 worker 的循环完成。

### 4.3 为什么成员写成 const IClock&

```cpp
const IClock& clock_;
```

含义是：对象借用一个外部时钟，经由只读接口获取时间，不负责销毁。main 的 SystemClock 必须活到使用者停止以后。

`const` 修饰接口调用权限，不代表时间不会变化。下一次读时钟仍可能得到新的数值。

### 4.4 ManualClock 用于测试可控时间

它有 `monotonic`、`wall` 两个公开整数，方法直接返回它们。测试可以让单调时间前进，同时让日历时间后退，从而验证超时判断没有误用日历时间。

这些普通整数没有 mutex 或 atomic，因此 ManualClock 本身不承诺“多个线程一边写一边读也安全”。当前单元测试中的可控使用，与生产 SystemClock 是不同场景。

阅读任务：在 `arm()` 找到读取 mono_ms 的地方，在 `begin()` 找到读取 wall_ms 的地方，并说明两者为什么不能互换。

## 5. `BoundedQueue<Event>`：多生产者与单业务消费者的交接处

源码：[support.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/support.hpp)。模板的实现就在头文件中。

### 5.1 职责与对象关系

`BoundedQueue<T>` 是模板类型；`BoundedQueue<Event>` 是用 Event 作为元素的具体类型；main 中的 `queue` 是这个类型的对象。

main 拥有它。仪器、工位、输入线程通过 sink 投递；业务线程通过 `pop()` 读取。队列只负责交接和容量限制，不解释 start、confirm 或 PASS 的含义。

### 5.2 全部重要成员

| 成员 | 含义 | 保护方式 |
|---|---|---|
| `capacity_` | 最大条数 | 构造设定，此后不修改 |
| `items_` | `deque<T>`，尚未消费的消息 | `mutex_` |
| `mutex_` | 保护队列的互斥锁 | 通过 RAII 锁使用 |
| `wake_` | 条件变量，唤醒等待消费者 | 与队列锁配合 |
| `closed_` | 已停止接受新元素 | `mutex_` |
| `overflow_` | 发生过满载拒收 | 独立 atomic |

### 5.3 push：接受一个值，尝试放入队尾

签名 `bool push(T value)` 表示按值接收。调用者可以传副本，也可以传一个允许移动的对象。

执行顺序：

1. 加锁，避免两个生产者同时修改 deque。
2. 若关闭，返回 false。
3. 若满载，设置 overflow，唤醒消费者，返回 false。
4. 把 value 移入队尾，唤醒消费者，返回 true。

**true 只表示已接收，不表示业务已经执行；false 也没有等待到空位再重试的承诺。**

push 没有条件变量等待“空位”的行为，但仍可能等待 mutex；不要把它理解为严格的无锁或绝对零阻塞接口。

### 5.4 pop：等待一段时间，再取队头

源码节选：

```cpp
wake_.wait_for(lock, wait,
               [this] { return closed_ || !items_.empty() || overflow_.load(); });
if (items_.empty())
    return false;
result = std::move(items_.front());
items_.pop_front();
return true;
```

`result` 是调用者的输出对象。只有返回 true，才能说本次取得一个新事件。

等待期间 unique_lock 暂时放开 mutex，生产者才有机会入队；醒来重新拿锁再检查条件。因此不能说消费者“持锁睡着，阻止生产者写入”。

队列按**实际入队顺序**取出。来自不同线程的事件，不能仅凭物理发生时间推断严格的先后顺序。

### 5.5 为什么 overflow 不做成另一条 Event

如果队列已经满了，再投递“队列已满事件”也可能失败。独立 atomic 标志不需要额外队列槽位。

`take_overflow()` 用 `exchange(false)` 读取并清除标志；业务线程收到这个证据后进入 fatal，不继续假设所有关键消息都完整到达。

多个生产者调用 sink 时通常不逐一处理 false，但满载标志能由业务循环统一观察。关闭导致的 false 则属于停止接收，不等同于新的 overflow。

### 5.6 close 不是清空

close 设置关闭状态并唤醒等待者。已有元素仍可 pop；新 push 被拒绝。

本节自查：queue 里存的是 Event，`InspectionWorker::candidates_` 里存的是候选测量。它们用途、生命周期、容量限制都不同，不能当成同一个缓冲区。

## 6. CandidateDisplay 与 sink：让按钮确认对象有明确身份

源码：[worker.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/worker.hpp)、[worker.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/domain/worker.cpp)、[main.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/app/main.cpp)。

### 6.1 CandidateDisplay 只保存“当前已展示候选编号”

它不保存厚度，不保存全部候选，不执行质量判断，也没有自己的线程。

| 成员 | 作用 |
|---|---|
| `current_` | 最近发布的候选编号；空字符串表示当前没有可绑定编号 |
| `mutable mutex_` | 保护发布、读取、清除操作；const current() 也能加锁 |

main 拥有这个对象。业务线程调用 publish/clear，工位线程经 sink 调用 current。

### 6.2 publish：日志展示与更新编号一起受锁保护

源码节选：

```cpp
void CandidateDisplay::publish(const Task& t, const Measurement& m) {
    std::lock_guard<std::mutex> lock(mutex_);
    log("candidate", "收到新候选，请明确确认编号",
        {{"inspection_id", t.id},
         {"point_index", t.points.size() + 1},
         {"candidate_id", m.candidate_id},
         {"milli_um", m.thickness_milli_um},
         {"substrate", m.substrate}});
    current_ = m.candidate_id;
}
```

当前项目的候选“展示”体现为输出 candidate JSON 日志，没有在这个类里创建图形界面。

日志完成、编号更新期间，current() 不能读到两者之间的状态。锁保护的是这两件事的关联，不仅是一个字符串赋值。

副作用也要看见：log 使用 stdout 并刷新。如果输出阻塞，publish 会延迟，也会让需要这把锁的读取等待。锁不会让 I/O 自动变快。

### 6.3 current 和 clear

`current()` 在锁内返回 `current_` 的**字符串副本**。释放锁后，调用者可以独立使用这份编号。

`clear()` 在锁内清空编号。开新窗口、确认点、中止、故障等路径都会让旧展示失效。

`mutable` 允许 const 方法操作锁。它不表示 const 方法可以随意修改候选业务内容。

### 6.4 sink 的类型和捕获关系

`EventSink` 是：

```cpp
using EventSink = std::function<bool(Event)>;
```

main 中的 sink 是 lambda，随后被保存为 EventSink。`[&]` 使它引用 main 中的 queue 和 display；复制这份可调用对象，仍会操作同一组共享对象。

sink 每次在**调用它的生产者线程**执行。它不会切换线程；真正的线程交接发生在 push 后，业务线程稍后 pop。

### 6.5 给快照绑定候选的具体问题

假设当前展示 A，但测量 B 已先入队、尚未被业务处理：

```text
1. 当前展示 A。
2. 测量 B 进入事件队列，但还没有展示。
3. 工位读取按钮快照；sink 读取当前展示 A，写入 e.bound_candidate。
4. 业务先处理 B，当前展示变成 B。
5. 业务处理按钮，confirm(e.bound_candidate)，确认 A。
```

如果步骤 5 才读取 display.current()，读到的会是 B，按钮关联对象就变了。

绑定的准确含义是：**在快照准备入队时，把当时读取到的已展示候选编号复制进 Event。** 这不是精确捕获物理按键瞬间；工位轮询仍有延迟。它防止的是投递以后、排队期间的新候选改变确认对象。

绑定编号加在 Linux 的 Event 上，既不写回 MCU，也不改变 Modbus 寄存器协议。每个 Snapshot 事件都绑定，只有相关按钮处理分支真正用到它。

如果编号为空、已被清除或不在当前窗口，confirm 会拒绝，不会自动改成“最新编号”。

## 7. BusinessHealth：证明业务循环仍在推进

源码：[support.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/support.hpp)。

源码节选：

```cpp
struct BusinessHealth {
    std::atomic<std::int64_t> last_loop_ms{-1};
    std::atomic_bool enabled{true};
};
```

它是共享数据对象，没有 run/start，也没有独立线程。

| 字段 | 谁写 | 谁读 | 含义 |
|---|---|---|---|
| `last_loop_ms` | 业务线程正常循环结束时 | 工位线程 | 最近一次业务推进时间；-1 表示尚无证据 |
| `enabled` | 业务故障/收尾和 main 停止阶段 | 工位线程 | 是否允许继续发送变化心跳 |

工位线程发送心跳需要同时满足：达到发送时刻、最近快照在线且版本匹配、enabled、业务健康戳存在且未超过 health_ms。

所以“串口能读写”并不足以证明业务能继续检测。如果业务被数据库、输出或测试 stall 卡住，last_loop_ms 不再更新，工位线程停止刷新变化心跳，现场模型/MCU 的独立保护可以发现这一点。

两项 atomic 分别保证独立读写的线程安全，不是把整个结构体变成一次原子事务，也不保证任意组合一定来自同一时刻。

阅读任务：在业务 run 找到 `last_loop_ms.store(...)`，在工位 run 找到 `.load()`，再看 fatal 怎样禁用 enabled。把“写证据”和“读证据”连起来。

### 8.6 生命周期：构造、start、run、停止

构造只保存依赖。start 通过以下语句启动线程：

```cpp
thread_ = std::thread([this] { run(); });
```

`[this]` 让新线程访问同一个 worker 对象。不会把整个 worker 复制到另一条线程。因此销毁之前必须 join，确保后台不再访问 this。

request_stop 只置原子标志，不直接关数据库。join 等待线程结束。析构也调用 request_stop/join 兜底；正常使用要求 start 只调用一次。

### 8.7 run：读懂“初始化—循环—收尾”三个阶段

**初始化：** 在业务线程创建仓库 → recover → 实际写探针 → 磁盘余量检查 → 生成 run_id 与时间质量 → 输出 service_ready。测试配置才设置最终提交前后的崩溃钩子。

**循环：**

1. 消费 overflow 标志，必要时 fatal。
2. pop 一个事件，最多等待 20 ms。
3. 调用 handle，异常转为业务/数据库故障。
4. 检查活动任务是否使用了过期工位快照。
5. 检查当前测量窗口是否到期。
6. 大约每秒检查磁盘空间。
7. 若未 fatal，更新业务健康戳。

**收尾：** shutdown → repo_.reset → finished_=true。初始化/收尾异常也会禁用健康并标记失败。

一个重要阅读细节：当前实现先 handle，再做这一轮的窗口超时检查。测量/confirm 的入口并没有独立检查所有截止条件。因此应理解为“循环检查到期并中止”，不要据此声称每个入口都严格拒绝截止时间之后的操作。

### 8.8 handle：所有外部输入在这里变成串行业务动作

| 分支 | 关键工作 |
|---|---|
| Stop | 设置停止标志 |
| InstrumentState | 活动任务遇断线/代次变化则中止，更新在线状态与代次 |
| Measurement | 检查窗口归属，保存候选，转 WaitConfirm 并展示 |
| Snapshot | 进入 snapshot(e) |
| CommandDone | 进入 command_done(e) |
| Cli | 进入 cli(e)，仍在业务线程 |

Measurement 的筛选条件值得逐条读：没有 fatal、有活动且 INSPECTING 的任务、处于等新测量或等确认、接收时间严格晚于 arm、连接代次一致、材料 FE/NFE。

符合这些条件不等于质量合格。250 μm 也可以作为候选并被确认，最终规则会判 FAIL；协议与窗口合法性、质量合格性是两次不同判断。

当前候选 map 独立限制 128 条。满了进入 fatal。这和可配置的公共事件队列容量不是同一个限制。

### 8.9 begin：创建任务后，还要等待 START 的现场证据

前置条件包括：没有 fatal、没有活动任务、没有未完成命令、安全同步成功、工位快照新鲜、MCU Ready、工件到位、健康非零、仪器在线。

随后验证工件编号、查找产品规则、检查磁盘、做真实写探针，再创建 Task：

```text
新检测 UUID
工件编号
规则副本
持久化分配的 token
创建时日历时间
```

执行 `repo_->create(...)` 成功后才设置 `task_`，阶段进入 StartPending，清空候选，调用 issue(Start)。

**begin 返回后，不一定已经可以 arm。** 必须等工位线程验证 START 执行成功，再由 command_done 把任务改为 Inspecting、阶段改为 WaitArm。

### 8.10 arm：为一个确认点建立归属条件

仅在合适的活动任务和 WaitArm 阶段允许执行，还要求仪器在线、快照可用、工件到位。

清空上一窗口候选与展示，然后记录：

```cpp
window_ms_ = clock_.mono_ms();
window_generation_ = generation_;
window_deadline_ = window_ms_ + cfg_.measurement_ms;
phase_ = InspectionPhase::WaitNewMeasurement;
```

arm 的作用是“业务允许接纳这个窗口的新测量”。它没有向仪器发送“现在开始物理测量”的命令。

之后新候选出现，不会延长这个 deadline。确认下一个点之前，必须再开启一个新窗口。

### 8.11 confirm：从候选到确认点，再到最终质量结果

先检查状态、快照、到位，再通过 id 在 candidates_ 中查找。找不到就拒绝，不自动确认最新候选。

源码节选：

```cpp
Point p;
p.index = static_cast<int>(task_->points.size()) + 1;
p.value = candidate->second;
p.confirmed_ms = clock_.wall_ms();
repo_->save_point(task_->id, p);
task_->points.push_back(p);
display_.clear();
candidates_.clear();
```

逐句的工程含义：

- index 按已有确认点推进。
- value 复制被选择候选，确定这次保存什么。
- confirmed_ms 与测量接收时间分开记录。
- 先保存数据库，成功才推进内存和显示成功。
- 清除本窗口候选，防止用于下一点。

点数不足：返回 WaitArm。点数满足：进入 Finalizing → 内存 passes → repo.complete 根据已保存数据复核并提交结果/Outbox → Task Completed → issue(ApplyResult)。

数据库提交点位与追加内存 vector 是两个动作。正常顺序避免“先显示成功后写库失败”；但如果数据库已提交后 vector 分配内存抛异常，不能靠数据库事务回滚已完成提交。这类异常由故障路径及重启恢复处理，不应把它称为整个函数的全局原子操作。

### 8.12 snapshot：从工位事实维护业务资格

建议按以下顺序对照源码，而不是直接跳到按钮：

1. 保存 previous，更新 snapshot_。
2. 离线：取消同步资格，中止活动任务，清除展示。
3. 版本不匹配：fatal 并停止健康心跳。
4. 初次上线或 MCU 重启：请求新 epoch 的安全同步。
5. 已开始的检测：持续验证到位、token、MCU Inspecting、健康。
6. 新外部故障：需要重新同步；HOST_ABORT 故障码 5 是主动中止的特殊情况。
7. 已完成工件正常离开且 MCU Idle：释放当前内存任务。
8. 处理尚未消费的锁存按钮事件。

MCU 重启识别结合 uptime 的无符号差值、Boot 状态变化、ACK epoch 变化。代码也考虑正常 32 位 uptime 回绕，不能只比较“新 uptime 小于旧值”就断定重启。

按钮通过 event_sequence 去重。ACTION 在 WaitArm 调用 arm，在 WaitConfirm 调用 `confirm(e.bound_candidate)`；RESET 根据条件签发复位。处理后发送 AckInput，让 MCU 清除这次锁存按钮。

### 8.13 synchronize 与 issue：建立命令身份并先记录意图

synchronize()：准备一个可信的新周期，并请求 MCU 回到安全状态。
issue()：给某个具体动作分配身份、留下记录、提交执行`

synchronize()` 等 commands_ 为空后，持久化分配新 host_epoch，重置命令/按钮序号，把阶段置 Fault，签发 SyncSafe。同步成功后仍等待人工 reset。

`issue()` 的流程：

```text
准备 Command(epoch、sequence、token、opcode、argument)
→ 仓库记录 PENDING
→ 放进业务 commands_ map
→ workstation.submit(c)
```

SyncSafe、ResetFault 的 token 为 0；其他命令按当前 Task 取 token。序号耗尽不能回绕复用，需要新同步周期或中止。

submit 返回 false 时记录 FAILED、移除 map 项并抛异常。成功返回只表示命令排队成功。

持久化记录放在提交之前，是为了进程突然退出后仍知道尝试过哪条动作；它没有把 SQLite 与串口发送变成同一个事务。

### 8.14 command_done：把异步反馈转为业务推进或故障

先丢弃旧 epoch 回调，再移除业务 map 对应项，更新 actuation_log：

| 结果 | 状态 | 含义 |
|---|---|---|
| `success=true` | ACKNOWLEDGED | 工位线程确认身份与后置状态满足 |
| detail 含 timeout 或 unknown | UNKNOWN | 无法证明是否已经执行 |
| 其他失败 | FAILED | 明确拒绝、状态不匹配、未发送离线等 |

成功时按命令推进：SyncSafe → synchronized=true 但仍 Fault；ResetFault → Ready/Idle；Start → 仓库 mark_started、Task Inspecting、WaitArm。

Start 失败会中止；ApplyResult 失败会保留已提交的质量结果，进入现场故障并尝试 Abort。PASS/FAIL 与执行确认是两种事实。

如果等待重新同步，要在旧命令全部收尾、通道条件合适后才新建 epoch。

### 8.15 abort、fatal、shutdown：三种收尾不能混淆

| 方法 | 触发目的 | 对历史质量结果的影响 |
|---|---|---|
| `abort(reason)` | 中止仍活动的检测 | 保留已确认点，不把中止改写为 FAIL；不修改已完成结果 |
| `fatal(reason)` | 系统可靠性已受损 | 设置失败标志、禁健康、停止新业务，尝试中止 |
| `shutdown()` | 服务要结束 | 保存活动任务中止，尽量撤销现场输出并有界等待命令结果 |

fatal 不直接设置 stop_requested。发生运行期致命故障后，进程可能继续存在供查询或等待退出；failed 标志决定最终失败退出码。

fatal 先设 phase Fault，但内部 abort 可能再把 phase 改成 Aborted。判断系统是否发生致命故障，应看 fatal_/failed_，不能只看 phase 名称。

shutdown 不继续常规测量业务，只在有限时间里处理命令结果、记录执行状态；设备线程此时还活着。等待结束后，数据库在业务线程内关闭。

### 8.16 辅助方法与 CLI 的位置

| 方法 | 作用 |
|---|---|
| `active()` | task_ 有值且状态 StartPending/Inspecting 才算活动 |
| `usable_snapshot()` | 在线、版本匹配、单调时间未超过 health_ms |
| `disk_ok()` | 数据库所在文件系统可用空间达到阈值，MiB 按 1024×1024 换算 |
| `status()` | 输出阶段、设备、候选点数、故障、待传数量等 |
| `cli()` | 解释操作命令，属于此类，定义在 commands.cpp |
| `finished()`、`failed()` | 给 main 提供 atomic 状态查询 |

本章建议精读顺序：构造与 start → run → handle 的 Measurement → begin → arm → confirm → issue → command_done → snapshot → abort/fatal/shutdown → commands.cpp。

读完应能解释：**为什么开始命令入队以后仍不能采样，为什么测量收到以后仍不能算确认点，为什么质量完成以后仍要等待现场执行确认。**

## 9. InspectionRepository 与 StorageError：让业务事实可以恢复和追溯

声明：[repository.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/repository.hpp)。实现：[repository.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/persistence/repository.cpp)。表结构：[001_init.sql](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/config/migrations/001_init.sql)。

可直接跳到：[构造与打开连接](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/persistence/repository.cpp:110)、[save_point](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/persistence/repository.cpp:236)、[complete](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/persistence/repository.cpp:264)、[recover](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/persistence/repository.cpp:165)。

### 9.1 职责与线程关系

业务层说“创建任务”“保存确认点”“完成检测”，仓库把这些动作落实为 SQL、约束和事务。

仓库不创建线程，也不在每个方法里把请求投递给数据库线程。`repo_->save_point(...)` 是普通同步函数调用，SQLite 操作仍在业务线程执行。

worker 的 run 通过 make_unique 创建它，正常结束前 reset。`db_` 连接只由该业务线程使用。SQLite 打开标志包含 NOMUTEX，当前设计依赖单线程独占，不能随意让其他线程也调用同一个仓库。

### 9.2 成员和复制规则

| 成员/声明 | 工程意义 |
|---|---|
| `sqlite3* db_` | SQLite C 句柄，仓库负责关闭 |
| `exec(sql)` | 执行固定 SQL 的私有工具，错误转成 StorageError |
| `checkpoint` | 可选测试回调，定位最终提交前后；生产默认空 |
| 删除复制构造、复制赋值 | 防止两个仓库对象误认为自己拥有同一个连接 |

`db_` 是裸指针，但并非“没人负责”。所有权由仓库构造/析构的实现明确管理。智能指针是表达所有权的一种办法，不是唯一办法。

### 9.3 构造函数是一个真实的资源申请过程

按以下顺序读：

1. 可写且不是 :memory: 时，按需创建父目录。
2. sqlite3_open_v2 打开连接；失败时释放可能已产生的句柄。
3. 设置 busy_timeout 和外键。
4. 检查 user_version，拒绝比程序支持版本更新的结构。
5. 只读模式到此返回。
6. 可写模式启用 WAL、synchronous=FULL。
7. 初次建库，在事务内执行编译期嵌入的迁移 SQL。

构造后面的步骤如果抛异常，类自己的析构函数不会被调用，因为对象还没构造成功。所以构造函数有 catch(...) 显式 close 再 rethrow。**这是理解 C++ 资源类的重要例子。**

FULL 提供更强的同步策略，但不能据此跳过操作系统和存储硬件的实际耐久性条件。

### 9.4 五张表分别保存什么

| 表 | 保存的事实 | 为什么要独立 |
|---|---|---|
| metadata | host_epoch、session_token、写探针等 | 身份分配跨重启持续递增 |
| inspection | 一次检测身份、规则、状态、结果、时间 | 主业务记录 |
| measurement | 已确认点及测量追溯信息 | 候选没有自动进入这张表 |
| outbox | 检测完成事件与待传状态 | 完成事实需要留下可发送的持久记录 |
| actuation_log | 现场命令身份、内容与执行状态 | 质量结果和设备动作结果不同 |

measurement 的 `(inspection_id, point_index)` 是主键，`(inspection_id, candidate_id)` 唯一，防止同任务重复点号或重复候选。

actuation_log 用 `(host_epoch, command_seq)` 唯一关联命令。outbox 限制同检测同事件类型只产生一条记录。

### 9.5 recover：恢复到可解释的安全状态

在一个事务中：

- 未完成的 START_PENDING/INSPECTING 任务改成 ABORTED，原因 service_restart。
- PENDING 的现场命令改成 UNKNOWN，因为重启已经丢失确认上下文。
- WAIT_REPLY/RETRY_WAIT 的云事件回到 PENDING，并清除旧 request_id。

recover 不会接着完成旧检测，不会把旧 PASS 输出重新发送到现场。保留历史，与恢复现场动作是不同责任。

### 9.6 allocate：持久化分配 epoch 与 token

只接受 `host_epoch`、`session_token` 两种键。事务中首次初始化为 0，读取旧值，检查 32 位耗尽，递增保存并提交，再返回新值。

因此分配出来的是非零身份。进程重启后不会简单从 1 重来。允许有分配了但后续未使用的间隙；核心要求是不能回绕复用旧身份。

### 9.7 创建、开始、保存点：每一步都有前置状态

| 方法 | 前置条件/重要动作 | 成功返回代表什么 |
|---|---|---|
| `create(t, quality, run)` | 插入身份、规则快照，初始 START_PENDING | 任务创建事务已提交 |
| `mark_started(id)` | 仅更新 START_PENDING，必须恰好一行 | 任务持久化进入 INSPECTING |
| `save_point(id, p)` | 同事务检查正在检测，点号=已存数量+1，未超要求 | 这一确认点事务已提交 |

mark_started 是单条 SQL 自动提交，不使用显式 Transaction 也不是“没有事务”。

save_point 的状态检查与 INSERT 在同一写事务中，避免只做内存检查后就随意写入。数据库约束为业务提供第二层核对。

### 9.8 complete：必须细读的最终事务
的状态检查与 INSERT 在同一写事务中，避免
完整拆解：

```text
BEGIN IMMEDIATE
  读取数据库里 INSPECTING 任务的规则快照与时间
  按 point_index 读取已经保存的确认点
  核对点号连续、点数正确、材料与厚度
  重新计算 PASS/FAIL
  核对调用者 Task.result 与计算结果一致
  更新 inspection 为 COMPLETED 并写结果
  生成稳定 event_id，构造完成事件 JSON
  插入 outbox
  可选 before_final_commit 测试钩子
COMMIT
可选 after_final_commit 测试钩子
```

为什么重新读数据库？因为最终完成要以实际已保存点为依据。只依赖 Task.points 缓存，会把缓存与持久化事实的偏差藏起来。

结果与 Outbox 在同一个事务，所以不会正常留下“结果已完成但完成事件没插入”的半套提交。

**原子范围是最终结果更新 + Outbox 插入。** 最后一个确认点的 save_point 是此前单独提交的事务；MCU 的 ApplyResult 则是完成后另一条异步动作，均不属于这个最终事务。

before 钩子抛异常时，未提交事务会回滚。after 钩子发生在提交之后，即便随后出现异常或进程退出，已经提交的事实仍然存在。这是不能只看“函数是否正常返回”判断数据库是否写过的例子。

### 9.9 其余关键方法

| 方法 | 核心工作 | 阅读注意 |
|---|---|---|
| `abort(id, reason, now)` | 仅更新未完成任务为 ABORTED | 不删除点，不覆盖已提交 PASS/FAIL |
| `record_command(id, c)` | 动作日志先记 PENDING | 空任务 id 转 SQL NULL，支持全局同步命令 |
| `acknowledge(c, status, detail, now)` | 按 epoch/seq 更新动作日志 | 不修改质量结果 |
| `query(key)` | 空键查全部，否则匹配检测/工件编号 | 返回 Json 数据副本，包含点与动作记录 |
| `outbox()` | 返回所有事件及状态、次数、载荷 | 不是只查询 PENDING |
| `pending_count()` | 统计 state 不是 PLATFORM_ACCEPTED 的记录 | 名称表示仍未得到平台接受确认 |
| `writable_probe()` | 对 metadata 做实际写事务并提交 | 比只看目录权限更能发现锁或真实写错误 |

query/outbox 的 const 表示接口不改仓库的 C++ 成员，不表示完全不操作 SQLite。查询仍会创建语句并推进结果游标。

### 9.10 StorageError：错误类型就是业务分类依据

```cpp
class StorageError : public std::runtime_error {
  public:
    using std::runtime_error::runtime_error;
};
```

它继承标准异常的消息构造能力，本身没有额外字段。价值在于类型：CLI 可以把 StorageError 识别为数据库可靠性问题，与普通操作参数错误分别处理。

本章建议精读：构造 → create → save_point → complete → recover → allocate → query/actuation。暂时不用背每条 SQL 的列号，先弄清表与事务的业务意义。

## 10. Statement、Transaction：两个小类教你理解资源管理

源码：[repository.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/persistence/repository.cpp)。它们位于匿名命名空间，只供本实现文件使用。

### 10.1 Statement：一条 SQL 语句的生命周期

| 成员 | 意义 |
|---|---|
| `db_` | 借用仓库的连接，不负责关闭 |
| `value_` | 自己负责的 sqlite3_stmt 句柄 |

构造 prepare，析构 finalize。仓库方法使用局部 Statement，离开作用域时释放语句，即使中间抛异常也会释放。

关键函数：

| 方法 | 用途 |
|---|---|
| `text(index, value)` | 绑定字符串参数，SQLITE_TRANSIENT 要求 SQLite 复制内容 |
| `integer(index, value)` | 绑定 64 位整数参数 |
| `row()` | sqlite3_step：ROW 返回 true，DONE 返回 false，其余抛 StorageError |
| `done()` | 预期执行无结果语句，若意外返回行则报错 |
| `integer(index) const` | 读取当前行的整数列 |
| `text(index) const` | 复制当前行文本，NULL 映射为空字符串 |
| `check(rc)` | 统一检查绑定返回码 |

`text` 与 `integer` 都有“绑定”和“读取”两种重载。参数数量不同，用途不同，不是同一个调用既绑定又读取。

**SQL 绑定序号从 1 开始，结果列号从 0 开始。** 读代码时在旁边写下 SELECT 列顺序，很多看似神秘的 `integer(2)` 就能理解。

教学流程，表达实际调用方式：

```cpp
Statement s(db_, "SELECT value FROM metadata WHERE key=?");
s.text(1, kind);     // 第一个 ? 绑定 kind
s.row();            // 推进到结果行
auto value = s.integer(0); // 读取第一列
```

文本读取返回 string 副本，不把 SQLite 的内部缓冲指针交给外部持有。因此 Statement 析构后，已经复制的字符串仍有效。

### 10.2 Transaction：把未提交回滚责任放到析构中

| 成员 | 意义 |
|---|---|
| `db_` | 借用同一 SQLite 连接 |
| `committed_` | COMMIT 是否已经成功，初始 false |

构造执行 BEGIN IMMEDIATE。commit 执行 COMMIT，成功才置 true。析构发现仍 false，就尝试 ROLLBACK。

因此你在源码看到：

```cpp
Transaction tx(db_);
// 多个 Statement 操作
tx.commit();
```

要读出：“这一作用域管理一组数据库修改，未到成功提交就离开，正常析构路径会回滚。”

作用域退出包括正常 return 与 C++ 异常展开。SIGKILL、`_exit()` 等不会运行普通析构；这种进程级中断需要数据库自己的事务恢复机制，不能解释为 C++ 析构在断电时运行。

### 10.3 两类对象如何协作

Transaction 不拥有所有 Statement。它们只是借用同一个 db_：前者管理事务边界，后者管理语句资源。局部变量离开作用域时按构造相反顺序析构。

仓库方法可以同时持有多个 Statement，但没有在多个线程里共享这些语句。

一个源码细节：这两个内部类目前没有显式删除复制操作，实际用法是局部创建、不复制。不要从“采用 RAII”推导出“任意复制它们也是安全的”，句柄类复制规则仍需单独设计。

阅读任务：在 complete 里找 tx.commit 前的两个写入语句，说明任意一个失败时，另一项为何不能单独成为已提交结果。

## 11. IInstrument 与 InstrumentEvents：从设备数据到业务事件

接口：[instrument.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/instrument.hpp)。内部实现：[instrument.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/instrument/instrument.cpp)。

### 11.1 IInstrument：调用方只关心统一能力

| 方法 | 谁调用 | 契约 |
|---|---|---|
| `start()` | main | 启动采集执行，尽快返回 |
| `stop()` | main、析构 | 请求停止并等待采集线程结束 |
| `test_control(Json)` | 业务测试命令 | 后端是否接受测试控制；真实 BLE 返回 false |
| 虚析构 | unique_ptr 销毁 | 经基类指针正确销毁实际派生对象 |

工厂返回 `unique_ptr<IInstrument>`。具体对象可以是 ReplayInstrument 或 BleInstrument，main 与业务不需要包含它们的完整类定义。

这些具体实现放在 cpp 的匿名命名空间里。“头文件没有声明”不代表项目里不存在，而是它们被限制为模块内部实现。

### 11.2 InstrumentEvents：两个后端共同使用的业务转换器

它不是业务 Worker，也不自行创建线程。它作为具体后端的值成员，被对应采集线程串行调用。

| 成员 | 作用 |
|---|---|
| `cfg_` | 配置副本，提供仪器身份与日志开关 |
| `clock_` | 借用时钟，记录接收时间 |
| `sink_` | 保存事件出口，可以复制/移动调用对象 |
| `parser_` | 回放字节使用的 FrameParser 实例 |
| `online_` | 当前适配层是否在线 |
| `generation_` | 每次上线递增的连接代次 |
| `sequence_` | 本采集对象的测量诊断序号 |
| `received_wall_`、`received_mono_` | 最近通知的接收时间 |
| `crc_errors_`、`protocol_errors_` | 错误累计计数 |

“两个后端共享转换”指共享这一类的实现与事件语义，不是两个后端线程共同操作同一个 InstrumentEvents 对象。实际按配置只创建一个后端。

### 11.3 connection：建立连接代次并隔离残留半帧

流程：parser.reset → 设置 online → 若上线 generation++ → 发 InstrumentState Event。

断线时 generation 不增加；下次上线再增加。业务用 generation 判定窗口是否仍属于同一连接。

真实 BLE 的半帧保存在 BluezReader 的另一实例内，那里也负责断线 reset。InstrumentEvents 的 parser 主要用于回放路径。

### 11.4 notification：先记录接收时间

根据配置可输出原始十六进制日志；如果在线，记录两个时钟值。

测量事件使用这些时间，而不是业务线程消费事件时的时间。否则队列等待较久时，旧测量可能被误判为 arm 之后的新测量。

当前源码在采样时间之前可能先输出 raw_notification 日志，因此开启日志带来的阻塞也会影响实际采样点。这里的时间是接收处理路径时间，并不是仪器内部物理测量时间。

### 11.5 measurement：厂商值变成拥有自身数据的业务值

源码节选：

```cpp
Event e;
e.kind = EventKind::Measurement;
auto& m = e.measurement;
m.candidate_id = uuid();
m.instrument_id = cfg_.device_name;
m.thickness_milli_um = value.milli_um;
m.substrate = std::string(thickness::material_name(value.material));
m.group = value.group;
m.wall_ms = received_wall_;
m.mono_ms = received_mono_;
m.generation = generation_;
m.local_sequence = ++sequence_;
sink_(std::move(e));
```

`auto& m` 只是给 e 内部的 measurement 起一个引用名字，方便赋值；没有创建第二份独立 Measurement。

转换补上业务身份、来源、接收时间、连接代次，再通过 Event 值传给队列。`value.group` 和材料文字被复制为自有 string，不保留厂商回调对象的临时引用。

这一层不检查产品厚度阈值，不知道当前任务选了哪种产品。过滤与最终判定留给业务层。

### 11.6 feed 与 diagnostic

回放路径 `feed(data)` 先 notification，再 parser.feed，然后把解析出的每条测量交给 measurement，最后累计并记录错误计数。

一次通知可以产生零条、一条、多条测量。如果一帧拆成多个通知，完成帧的最后一个通知时间用于转换；如果一块有多帧，这些测量共享该块的通知接收时间。

diagnostic 区分“本次错误”和“累计错误”。CRC 错误不会直接生成合法候选。

本章自查：InstrumentEvents::measurement 负责转换，InspectionWorker::handle 负责归属，passes 负责质量判断。它们没有互相代替。

## 12. ReplayInstrument：把可重复输入接入真实解析与业务路径

源码：[ReplayInstrument 定义](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/instrument/instrument.cpp:188)。先读构造与 apply，再读 run。

### 12.1 职责与所有权

main 的 `unique_ptr<IInstrument>` 实际拥有 ReplayInstrument。它自己包含 InstrumentEvents、回放表、控制队列、线程。

它模拟仪器输入时序，而不是模拟整个检测业务。任务、规则、数据库仍由实际业务代码处理。

### 12.2 重要成员

| 成员 | 作用 | 修改者/保护 |
|---|---|---|
| `cfg_` | 回放配置副本 | 构造后读取 |
| `events_` | 转换与投递测量 | 采集线程 |
| `items_` | JSONL 中的回放项 | 构造写入，运行读取 |
| `controls_` | 业务测试命令提交的控制项 | mutex 下跨线程交接 |
| `mutex_`、`wake_` | 队列/停止同步和唤醒 | 外部调用与采集循环 |
| `stopped_` | 停止标志 | mutex 下读写 |
| `thread_` | 回放采集线程 | start 创建，stop 等待 |

stopped_ 是普通 bool，但每个相关访问受同一 mutex 保护；“停止标志必须都是 atomic”不是通用规则。

### 12.3 构造：运行前先发现明显文件错误

打开 JSONL → 跳过空行与 # 开头行 → 解析 JSON → 提前校验 hex 和非负 delay_ms → 保存 items_ → 拒绝空文件。

它没有在构造时完整校验所有控制字段。connection、milli_um 等的类型和范围还会由 apply 解释。因此构造成功也不表示所有运行控制永远不会出错。

### 12.4 test_control：提交请求，不直接改采集状态

在锁内检查停止/容量（最多 128 项），复制 Json 到 controls_，通知 wake，返回。

调用来自业务线程，但 apply 运行在采集线程。这样 parser、online、generation 仍只由一个线程修改。

不要把 test_control 的 true 理解成“候选已产生”，它只表示控制项已被接受。

### 12.5 apply：三种输入怎么实现

| 控制字段 | 行为 |
|---|---|
| `connection` | 调 events.connection，产生上线/离线及代次信息 |
| `hex` | 解析十六进制字符串，再交 events.feed |
| `milli_um` | 合成完整厂商帧并计算 CRC，再交 events.feed |

合成测量走 26 字节帧：BB 帧头、命令 02、声明长度 24、小端厚度、材料码、组名和 CRC。

厚度采用最高位符号、其余 31 位绝对值，不能把普通负整数内存当协议补码直接复制。

**模拟 150 μm 没有绕过 FrameParser 直接制造一个候选 Event。** 这让回放/测试仍覆盖组帧、校验、业务转换路径。

### 12.6 run：控制优先，定时回放随后

先 events.connection(true)，设置 index 与下一回放时刻。每次循环在锁内等待最多约 10 ms 并取出一项控制，然后放开锁。

锁外 apply 控制，再检查是否到达下一回放时刻，必要时 apply 文件项。循环开关决定文件结束后是否回到开头；不循环时线程仍可接受控制和 stop。

解析和事件投递不在控制锁内长期进行，避免 test_control 被处理过程卡住。

这里定时回放用真实 steady_clock。它没有把所有调度统一委托给注入 IClock；IClock 用于事件时间，而调度等待还有真实时间来源，阅读测试时要分清。

### 12.7 错误和停止

apply 异常被 run 捕获，记录 replay_error 并报告离线；循环未必直接退出。后续要有有效的连接控制才能恢复在线测量。

stop 在锁内设置 stopped 并唤醒，释放锁后 join。若拿着 mutex 一直 join，采集线程可能无法拿同一把锁检查退出，造成等待相互卡住。

析构调用 stop，保证 events_、队列和回调对象销毁时线程已结束。

## 13. BleInstrument：蓝牙库与业务接口之间的适配对象

源码：[BleInstrument 定义](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/instrument/instrument.cpp:131)。

### 13.1 三个成员表达出整个职责

| 成员 | 职责 |
|---|---|
| `InstrumentEvents events_` | 转成业务事件 |
| `unique_ptr<thickness::BluezReader> reader_` | 拥有实际 BlueZ 读取器 |
| `std::thread thread_` | 执行阻塞的 reader.run |

BleInstrument 自己不重写厂商帧解析算法，也不直接操作 Task。

### 13.2 构造函数把回调“接线”

它准备 ReaderConfig 和 ReaderCallbacks：

| 回调 | 适配动作 |
|---|---|
| notification | `events_.notification(data, n)`，记录接收时间 |
| measurement | `events_.measurement(m)`，建立业务副本 |
| state=connected | `events_.connection(true)`，说明已连接且订阅成功 |
| state=reconnecting/stopped | `events_.connection(false)` |
| diagnostic | `events_.diagnostic(crc, protocol)` |
| error | 记录仪器诊断日志 |

源码节选：

```cpp
callbacks.measurement = [this](const thickness::Measurement& m) {
    events_.measurement(m);
};
```

这一行在构造时**保存未来要做的动作**，不是构造时就调用 measurement。以后 BluezReader 解析出数据，才执行这份 lambda。

lambda 捕获 this，要求 BleInstrument 活到回调结束。stop/join 保证了正常生命周期中的这一要求。

### 13.3 start 和 stop 的责任分工

start 创建采集线程，在线程中调用 reader_->run()。run 非零时，适配器报告离线并记录 BLE 初始化失败。

stop 先 reader.request_stop，再 join thread。request_stop 只发请求；join 才表示回调执行已经结束。

真实 BLE 不接受 test_control，返回 false。业务测试开关开启也不会把这个后端变成可注入假测量的后端。

### 13.4 与回放路径最容易混淆的区别

```text
真实 BLE：BluezReader 内的 FrameParser → measurement 回调 → InstrumentEvents.measurement
回放：InstrumentEvents.feed → 自己的 FrameParser → InstrumentEvents.measurement
```

共用的是 FrameParser 的算法和业务转换语义，不是同一个 parser 实例。InstrumentEvents::feed 不是 BLE 正常通知路径的统一入口。

## 14. FrameParser：流式字节如何变成厂商测量

声明：[thickness/protocol.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/vendor/thickness/include/thickness/protocol.hpp)。实现：[thickness/protocol.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/vendor/thickness/src/protocol.cpp)。

### 14.1 先认识解析器输出的两个结构体

`thickness::Measurement`：

| 字段 | 含义 |
|---|---|
| `micrometers` | double 的微米值，便于显示 |
| `milli_um` | 精确的协议整数，业务直接使用 |
| `material` | MaterialType 枚举，nfe/fe/empty/unknown |
| `material_code` | 原始材料字节 |
| `group` | 设备组名字符串 |

`ParseReport`：包含 `vector<Measurement> measurements`、本次 `crc_errors`、本次 `protocol_errors`。

一次 feed 返回报告，可能没有完整测量，也可能有多条。空报告不一定是错误，也可能只是半帧尚未补齐。

### 14.2 FrameParser 为什么必须是有状态对象

它唯一核心成员 `buffer_` 保存尚未消费的字节。

如果设备先送 10 字节、再送剩下 16 字节，需要同一个 parser 把两次通知拼起来。若每次通知都创建新的 parser，上一半就丢了。

它不创建线程、不加锁，要求对应采集线程串行调用。feed 会复制输入字节，不在调用后保留外部临时指针。

### 14.3 feed 的两个入口

```cpp
ParseReport feed(const std::uint8_t* data, std::size_t length);
ParseReport feed(const std::vector<std::uint8_t>& data);
```

vector 版本转调指针版本，避免两套解析实现。指针 + length 是描述一段内存，不意味着指针携带长度信息。

### 14.4 主解析循环逐步读

1. 把新字节复制到 buffer_ 尾部。
2. 搜索 0xBB 帧头，丢掉前面的噪声。
3. 不足 4 字节，保留并等下次。
4. 从偏移 2/3 按小端读取声明长度。
5. 声明长度不在 3～4096：计协议错误，删当前头一个字节，再搜索。
6. 实际帧长 = 声明长度 + 2；不足则保留半帧。
7. 计算并核对 CRC；错误则计数、删当前头，重新同步。
8. 命令 02 且声明长度 24：parse_realtime 生成测量；命令 02 长度不符计错误。
9. 消费整帧，继续尝试后续帧。

其他命令如果 CRC 正确，会被消费跳过，不都当协议错误。

“删一个字节重新找头”和“合法整帧一次删除”的差别很重要：损坏帧里可能还有后续有效帧头，不能盲目按坏长度跳掉全部内容。

4096 限制的是声明长度，不能简单推导为输入任意大小时 buffer_ 永远不超过 4096；新输入先插入缓冲，实际输入边界还由上层控制。

### 14.5 parse_realtime：把字段偏移读成协议

| 偏移 | 内容 |
|---|---|
| 0 | BB 帧头 |
| 1 | CMD=02 |
| 2～3 | 声明长度 24，小端 |
| 4～7 | 厚度，小端 32 位符号/绝对值 |
| 8 | 材料码，00=NFE、01=FE、02=空 |
| 9～24 | 16 字节组名 |
| 25 | CRC |

厚度解码源码节选：

```cpp
const bool negative = (raw & 0x80000000U) != 0U;
const std::uint32_t magnitude = raw & 0x7FFFFFFFU;
```

先拆符号与大小，再提升到 int64_t 并保留正负号。负测量不在这里悄悄变成 0；质量规则随后决定是否合格。

组名先复制固定 16 字节，再遇 NUL 截断，去掉尾部填充空格。这与“直接当无限长度 C 字符串读取”不同。

### 14.6 reset 与 crc8 工具

reset 清空半帧，连接变更时使用。否则旧连接残留字节可能和新连接数据组成一条假帧。

crc8 是独立函数：初值 0、多项式 0x07，覆盖 CMD/SIZE/DATA，不包括 BB 和最后 CRC。它是数据完整性校验，不是质量判定。

工位 Modbus 使用另一套协议/CRC处理，不要把仪器 CRC8 与 Modbus RTU 的校验混用。

对应测试：[unit.cpp 的 test_parser](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/tests/unit.cpp)。阅读半帧补齐、多帧、CRC 错误、reset、负值几个用例，通常比手算 CRC 更有助于理解对象职责。

## 15. BluezReader、Impl、ReaderConfig、ReaderCallbacks：真实 BLE 的工程组织

### 15.1 ReaderConfig：蓝牙读取器自己的配置

| 成员 | 含义 |
|---|---|
| `device` | 按设备名称、别名或 MAC 匹配 |

### 15.2 ReaderCallbacks：保存上层希望收到的通知动作

| 字段 | 参数 | 对上层的意义 |
|---|---|---|
| notification | 临时字节指针、长度 | 原始通知到达，先记录接收时间 |

| diagnostic | CRC/协议错误数 | 结构化错误统计 |

这些 std::function 成员可为空；emit 方法先判断是否注册。回调在调用 run 的采集线程上串行执行，不由新线程自动处理。

notification 指针只在本次回调期间有效。measurement 引用也不能在回调返回后作为长期数据保存；适配层要转换为自有值。

### 15.3 BluezReader 的公开对象很小

关键成员：

```cpp
std::atomic_bool stop_requested_{false};
std::unique_ptr<Impl> impl_;
```

公开函数：构造、析构、run、request_stop。构造创建 Impl，但不连接 D-Bus；run 委托 Impl；request_stop 只置 atomic。

BluezReader 没有 std::thread 成员，采集线程由外层 BleInstrument 创建。BluezReader 的 run 自己会阻塞运行 GLib 事件循环。

它显式禁止复制和移动，让对象地址与内部资源关系稳定。回调持有 this/owner 引用时，这种身份稳定很重要。

### 15.4 Impl：隐藏底层依赖和复杂资源

头文件只声明 `class Impl`，完整类定义在 cpp，这叫 PImpl。

工程收益是：上层只需要知道读取器接口，不必在所有包含此头文件的代码里暴露 GIO 类型、D-Bus 调用和资源成员。

| 成员组 | 主要成员 | 作用 |
|---|---|---|
| 依赖 | `owner_`、`config_`、`callbacks_` | 读停止请求，保存配置和动作 |
| GLib 资源 | `bus_`、`loop_` | 系统总线连接、事件循环 |
| 注册身份 | `properties_subscription_`、`retry_source_`、`stop_source_` | 撤销信号与定时器，0 表示无注册 |
| 目标路径 | `adapter_path_`、`device_path_`、`characteristic_path_` | 定位当前设备与通知对象 |
| 解析 | `parser_` | 跨通知组帧，断线时清空 |
| 重试 | `retry_count_`、`scanning_reported_` | 档位、减少重复搜索提示 |
| 生命周期 | `has_run_`、`cleaned_up_` | 每实例只 run 一次，清理只做一次 |
| 连接 | `connected_`、`notifying_`、`owns_connection_` | 是否已订阅、是否有责任断开连接 |

除 owner 的原子停止标志外，核心状态主要由 run 所在线程处理。

### 15.5 run：建立事件循环，不直接写“while 接收字节”

拒绝重复 run → 获取系统 D-Bus → 订阅 PropertiesChanged → 创建 GMainLoop → 注册首次连接定时器与停止检查 → g_main_loop_run → cleanup → 发 stopped。

GLib 循环根据定时器和 D-Bus 信号调用函数。这依然是持续运行，只是调度入口由事件循环管理。

初始化获取系统总线失败返回 1，重复运行返回 2，正常结束返回 0。BleInstrument 检查这个返回值。

### 15.6 C 回调桥：把 void* 还原为对象

源码节选：

```cpp
auto* self = static_cast<Impl*>(user_data);
```

GLib 保存 user_data，之后把它传回静态函数。静态函数不能直接访问某个对象的 this，因此先把 user_data 转回 Impl 指针，再调用对应成员。

重点入口：

| 静态桥接函数 | 后续动作 |
|---|---|
| `retry_static` | 清当前一次性重试 ID，调用 try_connect |
| `stop_check_static` | 读取 owner.stop_requested，必要时退出循环 |
| `properties_changed_static` | 捕获通知处理异常，转入 properties_changed |

properties_changed_static 是 noexcept 并有 catch。emit_* 也保护上层回调异常。阅读时不要扩大成“所有底层函数都绝不会抛异常”，应查看各函数自己的边界。

### 15.7 snapshot：扫描蓝牙对象，不是工位寄存器快照

本 cpp 还有匿名命名空间中的 `Snapshot`，保存适配器、设备、服务、特征路径及布尔状态。它与 `inspection::Snapshot` 完全不同。

流程：GetManagedObjects → 取适配器 → 按 Address/Name/Alias 找设备 → 在目标设备路径下找服务 UUID → 找属于该服务的通知特征 UUID → 释放 GVariant 引用 → 返回普通 C++ 数据。

辅助 `ManagedObject` 保存对象路径与 interfaces 的 GVariant 引用。它只是扫描期间的临时数据，没有自动析构释放逻辑；snapshot 末尾显式逐个 unref。

阅读这一段主要追踪：“我拿到了哪些引用，何时复制字符串，何时 unref”。

### 15.8 try_connect：连接成功与订阅成功是两步

1. 已停止或已连接则返回。
2. 重新扫描对象，拒绝缺少/未开启的适配器。
3. 没有目标设备时请求发现并安排重试。
4. 设备尚未连接则调用 Connect，并记录 owns_connection。
5. 等待 ServicesResolved 和目标特征出现。
6. 调 StartNotify，失败清理后重试。
7. 设置 notifying/connected，重置重试档位，尝试停止发现，发 connected。

上层仪器在线以**连接并订阅成功**为依据，不能只看到 Connect 的调用返回就认为已经能接测量。

services_timeout 当前用于计算 250 ms 间隔的尝试次数；每次 snapshot 的同步 D-Bus 时间也算实际耗时。因此它不是整个流程严格的 10 秒绝对上限。

### 15.9 properties_changed：真正的通知数据入口

检查当前特征路径和接口 → 取 Value 字节数组 → emit_notification → parser.feed → 诊断与每条测量回调 → unref 临时值。

Value 指针借用 GVariant 内存。parser 在释放前复制字节，上层转换在回调期间创建业务值，才能安全跨线程。

设备 Connected 变 false 时，清连接/订阅状态和特征路径，reset parser，报告重连，安排退避。

### 15.10 重试、错误出口与清理

| 函数 | 作用 |
|---|---|
| `schedule_retry()` | 避免重复注册，按档位安排一次性重试 |
| `call_no_args()` | Connect/StartNotify 等同步调用，统一释放 reply/GError |
| `disconnect_owned_device()` | 只断开自己建立的连接 |
| `emit_notification/measurement/state/error()` | 调用已注册动作，捕获回调异常 |
| `report_gerror()` | 复制错误文字后释放 GError |
| `cleanup()` | 幂等撤销定时器、停止通知、断自有连接、取消信号、释放 loop/bus |

如果借用本来就存在的设备连接，退出不会主动 Disconnect。owns_connection 记录的是释放责任，不只是“连接是否在线”。

request_stop 由其他线程设置请求；GLib 停止定时器通常约 100 ms 检查，但同步 D-Bus 调用会延迟响应。所以不能承诺 stop 一定在 100 ms 内返回。

本章建议顺序：公开接口 → Impl 成员 → run → try_connect → properties_changed → cleanup → snapshot 的 GVariant 细节。

## 16. Command、Snapshot 与协议工具：命令和确认怎样关联

声明：[inspection/protocol.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/protocol.hpp)。实现：[inspection/protocol.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/workstation/protocol.cpp)。

### 16.1 Command：动作要求与身份一起传递

源码节选：

```cpp
struct Command {
    std::uint32_t epoch = 0, token = 0, sequence = 0, argument = 0;
    Opcode opcode = Opcode::SyncSafe;
};
```

| 字段 | 回答的问题 | 生成位置 |
|---|---|---|
| `epoch` | 属于哪次主站安全同步周期？ | synchronize 分配，issue 使用 |
| `token` | 针对哪次现场检测？ | Task 创建时分配，issue 选择 |
| `sequence` | 这个周期的哪条命令？ | issue 递增 |
| `opcode` | 要做什么动作？ | 业务按流程指定 |
| `argument` | 动作参数是什么？ | PASS/FAIL、按钮事件编号等 |

重发同一命令，要保持身份和内容不变，不能每次重试都生成新 sequence。否则 MCU 可能把它当作新的动作执行。

六种 opcode：

| 名称 | 数值 | 含义 |
|---|---|---|
| SyncSafe | 1 | 安全同步，建立新 epoch，清任务，保持故障安全态 |
| Start | 2 | 绑定 token，进入检测 |
| ApplyResult | 3 | 应用质量输出，argument 1=PASS、2=FAIL |
| AckInput | 4 | 确认并清除指定锁存按钮事件 |
| ResetFault | 5 | 人工复位到 Idle/Ready |
| Abort | 6 | 撤销现场任务与结果输出，进入故障安全态 |

### 16.2 Snapshot：一次观察到的工位状态

| 字段 | 作用 |
|---|---|
| `online` | Linux 判断这次通道是否在线，不是 MCU 寄存器字段 |
| `state` | MCU Boot/Idle/Ready/Inspecting/Completed/Fault |
| `inputs` | 输入位，bit0 为工件到位 |
| `outputs` | 输出位，1=PASS、2=FAIL、4=FAULT、0=全清 |
| `fault`、`health` | 故障码与健康信息 |
| `heartbeat` | MCU 心跳字段 |
| `uptime` | MCU 运行时间，用于观察重启 |
| `token` | MCU 当前任务身份 |
| `ack_epoch`、`ack_sequence`、`ack_status` | 哪条命令、什么执行状态 |
| `event_sequence`、`event_code` | 锁存按钮事件身份与类型 |
| `reset_reason`、`errors` | 诊断信息 |
| `version` | 协议版本，要求 0x0200 |
| `mono_ms` | Linux 读取/发布状态的本地单调时间，检查新鲜度 |

`present()` 用 `(inputs & 1U) != 0` 检查最低位。即使还有其他输入位，也不会把它们当工件到位。

Snapshot 是值对象。业务中的 snapshot_ 是**最近处理到的快照**，不意味着它与物理现场始终实时一致；业务通过 mono_ms 检查是否过期。

### 16.3 encode/decode：业务结构与寄存器数组之间的边界

encode 把 Command 转成 9 个 16 位寄存器：epoch 高/低、token 高/低、sequence 高/低、opcode、argument 高/低。

decode 把 22 个寄存器变成 Snapshot。状态码大于 5 则拒绝；成功设置 online=true。

32 位字段按**高字在前，低字在后**组合。这是工位寄存器顺序；仪器厚度按小端字节解析是另一条协议路径。

这些函数不打开串口、不启动线程，纯粹转换数据。串口帧/响应由 ModbusTransport 和 libmodbus 处理。

### 16.4 command_satisfied：写成功不等于动作成功

先检查 online、协议版本、ACK epoch、ACK sequence、ACK status=1，再检查对应动作的后置条件：

| 命令 | 还需要看到什么 |
|---|---|
| SyncSafe | MCU Fault、token=0、outputs=4 |
| Start | MCU Inspecting、token 匹配、工件到位、outputs=0 |
| ApplyResult | MCU Completed、token 匹配、工件到位、结果输出匹配 |
| ResetFault | Idle/Ready、token=0、outputs=0 |
| Abort | Fault、token=0、outputs=4 |
| AckInput | event_code 清零 |

因此一条旧 ACK 即使显示“曾经成功”，现场已经进入 Fault，也不会被当成当前 ApplyResult 成功的证据。

这个函数验证当前命令的执行后置条件，不是对任意 Command 参数的完整合法性验证。业务和 MCU 模型还有自己的状态、参数检查。

`opcode_name()` 将枚举变成日志字符串，是辅助观察，不参与实际设备执行。

## 17. IWorkstation 与 WorkstationWorker：调度一个异步工位

接口：[workstation.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/workstation.hpp)。实现：[workstation.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/workstation/workstation.cpp)。

可直接跳到：[WorkstationWorker 定义](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/workstation/workstation.cpp:318)、[submit](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/workstation/workstation.cpp:343)、[run](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/workstation/workstation.cpp:381)。

### 17.1 IWorkstation：业务提交要求，设备线程回报事实

| 方法 | 含义 |
|---|---|
| start | 创建工位通信线程 |
| stop | 请求停止并等待通信线程退出 |
| submit(Command) | 接受待发送命令，返回是否入队 |
| test_control(Json) | Mock 测试状态注入入口 |

submit 不等待 MCU 动作确认。若业务同步等串口，会影响健康推进、候选处理与超时调度。因此确认结果通过 EventKind::CommandDone 异步返回。

工厂始终返回一个 WorkstationWorker，只是它内部选择不同 Transport。不要理解为 make_workstation 直接把 ModbusTransport 当 IWorkstation 返回。

### 17.2 对象卡片

| 项目 | 内容 |
|---|---|
| 创建/拥有 | main 的 unique_ptr<IWorkstation> |
| 自己拥有 | Transport、通信线程、待发命令队列、测试控制队列 |
| 借用 | IClock、BusinessHealth |
| 保存 | Config 副本、EventSink 调用对象 |
| 外部调用 | 主线程 start/stop，业务线程 submit/test_control |
| 核心修改 | 通信线程 run，传输与 pending 状态单线程独占 |

### 17.3 全部重要成员

| 成员 | 作用 | 同步方式 |
|---|---|---|
| `cfg_` | 轮询、响应、期限、后端参数 | 运行读取 |
| `clock_` | 时间判断 | 借用接口 |
| `health_` | 是否允许变化心跳 | 读取其 atomic |
| `sink_` | 投递 Snapshot/CommandDone | 调用时进入共享事件队列 |
| `transport_` | 唯一底层传输对象 | run 操作，无外部共享读写 |
| `commands_` | 等待取出执行的 deque，最多 8 条 | mutex |
| `controls_` | Mock 测试控制 deque，最多 128 条 | mutex |
| `mutex_` | 保护两个交接队列 | 入队/取出短临界区 |
| `stopped_` | 跨线程停止请求 | atomic |
| `thread_` | 工位线程句柄 | start 创建、stop join |

transport_ 在构造时创建，实际串口 connect 在 run 中。Mock 构造会初始化状态，后续行为才由工位线程独占。

### 17.4 submit 和 test_control：锁内只负责交接

submit 在锁内检查 stopped 或队列满，成功 push_back 后返回 true。没有阻塞等待串口响应，但仍会拿互斥锁。

test_control 首先要求 mock 后端，锁内检查控制容量、复制 Json。实际 transport.control 由 run 稍后调用。当前 test_control 没有与 submit 完全相同的停止检查，不要把两个函数的细节当成一致。

锁外才做通信：这样单次串口响应等待不会一直占用入队锁。

### 17.5 run 的局部变量也是对象状态的一部分

有些重要状态没有声明在类 private 区，而是在 run 内跨循环保存：

| 局部变量 | 保存什么 |
|---|---|
| `connected` | 底层是否已连接 |
| `next_connect` | 下一次允许重连时刻 |
| `next_poll` | 下一次读快照时刻 |
| `next_heartbeat` | 下一次变化心跳时刻 |
| `reconnect` | 连续连接失败的退避档位 |
| `heartbeat` | 发送给 MCU 的变化计数 |
| `pending` | 当前正在等待业务 ACK 的唯一命令 |
| `deadline` | 当前 pending 的总截止时间 |
| `next_retry` | 下次发送/重发时间 |
| `transmissions` | 当前 pending 已发送次数 |
| `snapshot` | 通信线程最近读到的快照 |

这些局部变量活到整个 run 返回，不是每轮循环重新创建。阅读变量生命周期时，注意声明位于 while 外还是 while 内。

`pending` 最多一条，commands_ 最多八条等待。队列容量八不意味着同时八条命令都在等待现场 ACK。

### 17.6 run 调度步骤一：连接和接收待办

如果未连接，达到 next_connect 才 connect；没到时短暂等待并继续检查 stop。连接成功重置退避，并让轮询/心跳尽快进入调度。

在 mutex 内交换出 controls_，若 pending 为空则从 commands_ 取一条。此时设置 deadline=now+command_ms、next_retry=now、transmissions=0。

**命令总期限在取成 pending 时建立，不是 submit 入队时建立。** 如果前面有命令，等待队列时间不计入这段 pending 期限。准确地说，deadline 用本轮开头采样的 now 计算；如果此前 connect 已经花了时间，剩下的实际等待时间会相应缩短。

然后放开锁，解释取出的测试控制。

### 17.7 run 调度步骤二：优先决定是否发健康心跳

检查到发送时刻、快照在线/版本匹配、健康 enabled、last_loop_ms 非负且新鲜，才：

```cpp
transport_->heartbeat(++heartbeat);
```

工位线程负责实际发送，业务线程负责提供推进证据。通信成功不能代替业务健康。

心跳事务也花时间，所以之后重新取 now，再决定命令是否过期或可以重发。

### 17.8 run 调度步骤三：同一命令的有界重发

到 deadline 就产生 business_ack_timeout，pending 清空。未到截止、达到 next_retry 且次数允许，调用 transport.command(*pending)。

允许首次发送 + retries 次额外重发。默认 retries=2，所以最多尝试三次；间隔按 command_ms/(retries+1) 分摊。

重发保持同一个 Command，不重新分配 epoch/seq/token。幂等判断需要稳定身份。

单次调用有自己的响应期限，命令还有业务确认总期限。两种期限解决的问题不同。

### 17.9 run 调度步骤四：轮询并验证 ACK

到 next_poll 读 22 字快照，记本地时间并 publish，再安排下一轮。

pending 的确认先匹配 ack_epoch、ack_sequence、非零 ack_status，并要求快照采样时刻不晚于 deadline；随后 command_satisfied 检查成功状态和后置条件。

成功发 done(executed)。匹配到明确拒绝或状态不满足，发 done(ack_rejected_or_state_mismatch)。等到总期限仍无合适确认，发 done(business_ack_timeout)。

publish 在同一轮中先发 Snapshot，后续 done 再发 CommandDone。它们用途不同：前者报告现场状态，后者终结一条 pending 命令。

### 17.10 publish 与 done：两种事件封装

| 方法 | 输出事件 | 内容 |
|---|---|---|
| `publish(Snapshot s)` | Snapshot | 快照值副本和本地时间，sink 补候选编号 |
| `done(c, success, detail, snapshot)` | CommandDone | 原命令身份、结果、说明、验证所用快照 |

CommandDone 不走“给按钮绑定候选”的分支，因为它的 kind 不是 Snapshot。

业务收到 success=true 时，依然要通过 e.command 确定是 Start、SyncSafe 还是 ApplyResult，不能只看一个布尔值就统一推进到同一阶段。

### 17.11 通信异常：区分“未发出”和“可能已经执行”

catch 路径关闭传输，置离线，发布快照：

- pending 已经进入执行流程，报告 transport_unknown，业务记录 UNKNOWN。
- 仍在 commands_ 中尚未发送的命令，逐条报告 transport_offline，业务记录 FAILED。
- 按 1/2/4/8/10 秒连接退避；连接成功重置档位。

为什么 pending 不能直接判 FAILED？例如 MCU 已执行，但响应在传输中丢了。Linux 无法证明动作没有发生，因此必须保留“未知”这个状态。

### 17.12 stop 和析构

stop 设置 atomic stopped，然后 join。run 检查后退出，当前 pending 产生 service_stopping 反馈，最后关闭 transport。

单次通信或等待没完成时，stop 不会瞬间中断所有调用。正常 main 先让业务有界收尾，再停工位。

本章精读顺序：成员 → submit → run 局部变量 → 取 pending → 心跳 → 重发 → 轮询/确认 → 异常 → stop。

## 18. Transport、ModbusTransport、MockTransport：调度和设备行为的分层

源码：[workstation.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/workstation/workstation.cpp)。三个类型都隐藏在实现文件里。

### 18.1 为什么 IWorkstation 下面还需要 Transport

两层接口服务不同调用者：

| 接口 | 调用者 | 提供什么 |
|---|---|---|
| IWorkstation | main、业务线程 | 启停和异步 submit |
| Transport | 工位线程 | 同步 connect/read/heartbeat/command |

WorkstationWorker 管“什么时候连接、什么时候发、等哪个 ACK、如何重试”；Transport 管“一次通信或模拟动作怎样完成”。

替换 Modbus/Mock 时，调度逻辑保持同一份实现。这是接口分层的实际用途。

### 18.2 Transport 的全部能力

| 函数 | 意义 |
|---|---|
| connect | 建立底层通信状态 |
| close | 清理底层资源/连接状态 |
| read | 得到一个 Snapshot |
| heartbeat(value) | 写入变化心跳 |
| command(c) | 交付命令，尚不承诺业务执行确认 |
| control(Json) | 默认返回 false，Mock 覆盖处理测试控制 |

它有虚析构，保证 unique_ptr<Transport> 销毁具体实现时释放相应资源。接口本身没有线程。

### 18.3 ModbusTransport：一个串口会话的拥有者

成员：

| 成员 | 含义 |
|---|---|
| `cfg_` | 串口、从站、期限配置副本 |
| `ctx_` | libmodbus 会话句柄，初始 nullptr，close 释放 |
| `last_end_` | 上一事务结束时刻，控制请求间隔 |

构造保存配置，不打开设备。connect 先 close 旧资源，再 modbus_new_rtu 创建 8E1 主站，设从站、关闭库自动恢复、设响应超时与 byte timeout，最后 modbus_connect。

关闭自动恢复是为了让 WorkstationWorker 统一解释断线、待确认命令未知与重连，不把恢复动作藏在库里。

关键函数：

| 方法 | 实际操作 | 成功条件 |
|---|---|---|
| read | FC04，从地址 0 读 22 个输入寄存器 | 返回完整 22 字，再 decode |
| heartbeat | FC06，写 0x0100 | 完整写一个寄存器 |
| command | FC16（十六进制 0x10），从 0x0110 写 9 字 | 完整写 9 字，但仍需随后业务 ACK |
| guard | 检查 ctx，等待距 last_end 至少 1750 μs | 避免连续请求间隔过小 |
| finished | 更新 last_end | 供下一次 guard 使用 |
| fail | 将 errno 转成 Modbus 错误异常 | 交上层处理 |
| close | modbus_close → modbus_free → ctx=nullptr | 可重复清理 |

guard 的请求间隔是代码层措施，不是整个物理 RS485 时序已经验证的证据。这里没有 MCU 固件，也不能从 PTY 模拟推断实机电气行为。

析构调用 close 兜底。正常传输读写由工位线程独占；不要把 ctx 拿给业务线程直接用。

### 18.4 MockTransport：在内存中表达 MCU 状态与规则

它没有串口句柄，不经过 RTU 字节发送。WorkstationWorker 的调度、命令等待与 command_satisfied 仍正常运行。

初始状态：online、协议版本正确、MCU Fault、fault=6、outputs=4、health=3。需要安全同步和人工 reset 后才进入可开始状态。

| 成员 | 作用 |
|---|---|
| `clock_` | 计算 uptime 和心跳新鲜度 |
| `s_` | 模型当前现场状态 |
| `connected_` | 模拟传输连接开关 |
| `started_` | 模型启动时刻，计算 uptime |
| `last_health_` | 最近收到变化心跳的时刻，初始 -1 |
| `last_heartbeat_` | 前一个主站心跳值 |
| `epoch_`、`last_sequence_` | 当前主站周期和最大已处理序号 |
| `have_command_`、`last_command_`、`last_status_` | 最近命令及缓存 ACK，用于重复请求判定 |

connect/close 改连接开关。read 先 tick 保护，再返回 s_ 副本并填 uptime/online。

### 18.5 Mock 的 heartbeat、fresh、tick

只有 heartbeat 值与上一次不同，才刷新 last_health；重复发送同一数字不代表持续业务推进。

fresh 判断变化心跳是否在 1500 ms 内。这个 1500 是 Mock 的现场保护期限，和 Linux cfg.health_ms 默认 500 是不同层的条件。

建立 epoch 后若不 fresh，tick 设置故障、清 token、输出 FAULT。通信线程即便继续 read，也不能掩盖业务停滞。

### 18.6 Mock 的 command：状态机与重复命令

先 tick，再处理：

1. 与最近命令 epoch/sequence 相同：内容一致返回缓存 ACK；内容不同返回冲突，不重新执行。
2. 普通命令要求当前 epoch 且序号前进；SyncSafe 可以建立更大的非零 epoch。
3. 按 opcode 检查状态、token、参数、健康，必要时改变 s_。
4. 写回 ack_epoch、ack_sequence、ack_status，缓存本次命令身份与状态。

| 命令 | 模型的主要检查/动作 |
|---|---|
| SyncSafe | 新非零 epoch，清任务、清按钮，保持 Fault 输出 |
| AckInput | argument 必须是当前事件序号，事件存在，然后清 event_code |
| ResetFault | 心跳新鲜、健康非零，清任务/故障，按到位选 Ready/Idle |
| Start | Ready、到位、非零 token、健康；进入 Inspecting |
| ApplyResult | Inspecting、token 匹配、参数 1/2、心跳新鲜；进入 Completed 并输出 |
| Abort | 不能清除不同 token 的任务；清 token、进入 HOST_ABORT Fault |

ACK 状态码：1=成功、2=状态不允许、3=token 无效、4=身份冲突、5=健康失败、6=参数无效。

缓存成功 ACK 不代表当前现场仍保持那个成功状态，所以 WorkstationWorker 还要调用 command_satisfied 验证当前后置条件。例如旧 PASS ACK 不能把后来的 Fault 重新当成 PASS 已应用。

### 18.7 Mock 的 control：控制也由工位线程执行

| 控制 | 行为 |
|---|---|
| present | 改到位输入；检测中离位故障，完成后离位回 Idle |
| button | 锁存 ACTION/RESET 事件；已有事件未确认时增加 errors，避免覆盖 |
| reset_mcu | 清主站周期/ACK/token，重置启动时间，回故障安全态 |

提交 JSON 与修改 s_ 分开，避免业务线程直接写现场模型状态。

项目另有 [workstation_sim.py](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/tools/workstation_sim.py) 的独立 PTY 模拟器，用真实 ModbusTransport 验证串口协议路径。它与 MockTransport 是不同实现，不应假定每个参数边界完全一致；两者都不代替真实 MCU 固件和硬件验证。

## 19. ICloudPublisher、DisabledCloudPublisher、CloudReply：明确当前实现边界

源码：[cloud.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/cloud.hpp)、[cloud.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/cloud/cloud.cpp)。

### 19.1 接口预留了“提交”和“最终接受”的区别

| 类型/成员 | 含义 |
|---|---|
| `PublishSubmission::Submitted` | 请求已被提交，不等于平台接受 |
| `NotConfigured` | 尚未配置适配器 |
| `Failed` | 提交失败 |
| `CloudReply::event_id` | 稳定的业务事件身份 |
| `CloudReply::request_id` | 某一次发送尝试身份 |
| `CloudReply::platform_accepted` | 是否有平台明确接受证据 |
| `CloudReply::error` | 回复错误说明 |

同一个完成事件未来可能发送多次，所以 event_id 稳定，而 request_id 区分发送尝试。这与工位命令的 epoch/sequence 机制属于不同通道，不能混用身份。

ICloudPublisher 的方法：status 返回状态，publish 接收业务事件、request_id 和未来回复回调，stop 清理未来适配器工作。

### 19.2 当前只创建 DisabledCloudPublisher

它没有网络连接、没有上传线程、没有排队成员：

- status 恒为 NOT_CONFIGURED。
- publish 返回 NotConfigured。
- 不调用成功回复回调。
- stop 无需工作。

当前 InspectionWorker 直接包含这个具体对象，主要读取 status；完成事件由 Repository 写入本地 Outbox，并没有一条已经实现的后台上传链路。

所以阅读时要区分：**接口已经设计、事件已经保存、云平台发送尚未接入。** 本地 Outbox 存在不能证明云上传成功。

## 20. CLI 为什么没有一个 CliWorker 类：函数同样可以组织模块

源码：[cli.hpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/include/inspection/cli.hpp)、[cli.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/cli/cli.cpp)、[commands.cpp](/home/ubuntu/桌面/BLE_Linux/coating_inspection_host/src/cli/commands.cpp)。

### 20.1 cli_loop：一个输入线程入口函数

main 用 std::thread 启动它，不必为了拥有一个循环而再定义 CliWorker 类。

| 参数/局部变量 | 用途 |
|---|---|
| input_fd | 标准输入文件描述符 |
| stop_fd | 停止管道读端 |
| sink | 投递 Cli 事件的可调用对象 |
| stopping | 查询主线程停止原子标志的回调 |
| line | 跨 read 保存尚未完整的一行 |
| data[512] | 一次 read 的临时字节块 |

poll 同时观察输入和停止管道。read 可能得到半行或多行，所以逐字符拼 line，遇换行才构造 Event.text。忽略回车，单行限制 4096 字节。

e.text 是 line 的副本，之后 line.clear 不会清掉队列里的命令。

stdin EOF 只结束输入线程，不自动结束服务。主线程继续等待信号或业务 finished。

### 20.2 cli_words：文本解析在业务线程发生

它用 istringstream/std::quoted 分解一行，支持双引号内空格，返回 vector<string>。

**读取文字**在输入线程，**解释文字和执行命令**在业务线程。cli.cpp 的文件名不能决定其中每个函数在哪个线程运行。

### 20.3 InspectionWorker::cli：属于业务类的成员

函数定义虽在 commands.cpp，完整名称仍是 InspectionWorker::cli，因此可以访问 cfg_、repo_、task_ 等成员。它没有创建第二个业务 Worker。

| 命令组 | 后续行为 |
|---|---|
| status/query/outbox/export | 业务线程读取仓库或导出数据 |
| start/arm/confirm/cancel | 调 begin/arm/confirm/abort |
| reset | 必要时先同步，满足条件后 issue ResetFault |
| quit | 设置业务停止请求，由 run/main 收尾 |
| sim | 先检查 allow_test_controls，再提交后端控制或测试故障 |

正常操作条件主要在对应业务方法里检查，CLI 负责参数和命令选择。

### 20.4 异常边界要看 try 的位置

StorageError、Json 异常在 cli 的处理范围内转 fatal；普通 std::exception 记录 cli_error。

但 `cli_words(e.text)` 位于此方法的 try 之前。如果解析器抛异常，会传播到 run 处理 handle 的外层 catch，可能进入 fatal。因此不能笼统断言“所有命令格式错误都只输出提示”。

同样，普通运行错误从哪里进入、在哪层被捕获，决定实际后果。阅读工程不能只根据注释或异常名称想当然。

测试 sim stall 会真正阻塞业务线程，用来验证心跳保护；sim overflow 直接调用 fatal，模拟同样的故障路径，并不是实际把公共队列填满。

## 21. 用三条调用链把对象串起来

下面是调用顺序说明，没有额外加入一张复杂架构图。边读边在源码中找到每一步，并标注执行线程。

### 21.1 测量到确认点：在哪里跨线程，在哪里入库

以 BLE 路径为例：

| 步骤 | 线程 | 对象/函数 | 数据与作用 |
|---|---|---|---|
| 1 | 仪器 | Impl.properties_changed | 收到 Value 临时字节 |
| 2 | 仪器 | notification 回调 → InstrumentEvents.notification | 记录通知时间 |
| 3 | 仪器 | FrameParser.feed | 复制字节、组帧、CRC、解码 |
| 4 | 仪器 | measurement 回调 → InstrumentEvents.measurement | 厂商值转自有 Measurement，加 UUID/代次 |
| 5 | 仪器 | sink → queue.push | Event 移入共享队列 |
| 6 | 业务 | queue.pop → handle | 跨线程交接完成，按窗口筛选 |
| 7 | 业务 | candidates_.emplace → display.publish | 保存候选，输出展示 |
| 8 | 输入或工位 | 投递明确确认操作 | CLI 携带 id，按钮快照由 sink 绑定 id |
| 9 | 业务 | confirm(id) | 候选复制成 Point |
| 10 | 业务 | repo.save_point | SQLite 事务保存 |
| 11 | 业务 | task.points.push_back | 更新确认点内存列表，回 WaitArm 或完成 |

要区分三个时间：通知接收时间、业务消费时间、人工确认时间。它们可能相差很大。

候选从设备路径进入内存；**只有确认后**才成为 measurement 表里的确认点。收到合法帧不自动增加 Task.points。

### 21.2 工位按钮到确认：三个编号各自管一件事

| 编号 | 所在位置 | 用途 |
|---|---|---|
| event_sequence | MCU Snapshot | 防止锁存按钮被多次轮询重复执行 |
| bound_candidate | Linux Event | 固定这条快照关联的候选 |
| command sequence | AckInput Command | 追踪“清除这次按钮”的命令执行 |

流程：

```text
工位线程读到 Snapshot(event_code=ACTION, event_sequence=17)
→ publish
→ sink 复制 display.current 到 e.bound_candidate
→ queue
→ 业务 snapshot 检查该按钮事件是否已见过
→ WaitConfirm 时 confirm(e.bound_candidate)
→ issue(AckInput, 17)
→ 工位线程提交并验证清除按钮
```

event_sequence=17 不等于候选 id，也不等于新发 AckInput 的 sequence。把这三个身份分开，按钮逻辑就容易读懂。

ACTION 在 WaitArm 是开窗口，在 WaitConfirm 才是确认。按钮语义由业务阶段决定，不是任何时候按 ACTION 都保存最新测量。

### 21.3 最后一个确认点到现场输出：四次承诺

| 阶段 | 承诺完成了什么 | 还没有证明什么 |
|---|---|---|
| save_point 返回 | 最后一个确认点已提交 | 整个质量结果已经完成 |
| complete 提交 | 质量结果与 Outbox 已保存 | MCU 输出已经变化 |
| workstation.submit=true | ApplyResult 接受排队 | 命令已经发送/执行 |
| CommandDone success=true | ACK 身份和现场后置条件满足 | 云平台已经接受结果 |

调用链：

```text
业务 confirm
→ save_point
→ passes
→ complete（结果 + Outbox）
→ issue ApplyResult（先记动作 PENDING）
→ 工位 submit 队列
→ pending → Transport.command
→ 轮询 Snapshot
→ command_satisfied
→ CommandDone 事件队列
→ 业务 command_done 更新 actuation_log
```

假设质量 PASS 已提交，而 ApplyResult 超时：数据库质量仍 PASS，动作日志 UNKNOWN，业务进入现场故障处理。未知表示缺少执行证据，不表示测量质量变成 FAIL。

### 21.4 一张小表检查共享数据与独占数据

| 数据 | 所在对象 | 谁修改 | 谁读取/消费 | 同步方式 |
|---|---|---|---|---|
| 待业务处理的 Event | main.queue | 各生产者 | 业务线程 | mutex、条件变量、overflow atomic |
| 当前展示 id | main.display | 业务线程 | 工位线程经 sink | mutex，返回副本 |
| 业务健康信息 | main.health | 业务、退出时 main | 工位线程 | atomic |
| 当前任务/候选/阶段 | InspectionWorker | 业务线程 | 业务处理方法 | 单线程独占 |
| SQLite 连接 | InspectionRepository | 业务线程 | 仓库方法 | 单线程独占，事务 |
| 等待工位发送的命令 | WorkstationWorker.commands_ | submit 与 run | 工位线程 | mutex |
| 当前 pending/快照/计时 | WorkstationWorker.run 局部变量 | 工位线程 | 工位线程 | 单线程独占 |
| 回放测试控制 | ReplayInstrument.controls_ | test_control 与 run | 仪器线程 | mutex、条件变量 |
| 仪器半帧与转换状态 | FrameParser/InstrumentEvents | 仪器线程 | 仪器线程 | 单线程独占 |

这个工程并不是“所有对象都线程安全”。它组合了两种策略：共享交接点加同步，核心可变状态限制在单线程内。

### 22.3 C++ 写法的工程翻译

| 源码写法 | 在这个项目里应该读成什么 |
|---|---|
| `const Task& t` | 临时借用任务只读，不复制整个任务，不延长寿命 |
| `Event e` | 当前函数拥有独立的事件值，可补字段再移动交接 |
| `auto& m = e.measurement` | 引用事件内部成员，后续赋值直接修改 e |
| `unique_ptr<IInstrument>` | 拥有一个可替换的仪器实现，虚析构正确收尾 |
| `optional<Task>` | 可以没有任务，有值也还要检查业务状态 |
| `map<string, Measurement>` | 用候选身份查询一份测量，不是按厚度排队 |
| `deque<Command>` | 等待取出的命令 FIFO，和等待反馈 map 不同 |
| `[this]` | 回调访问同一个对象，必须保证它活到回调结束 |
| `[&]` | 借用外部变量，不延长寿命，生命周期由 main 管 |
| `std::move(e)` | 允许转移内部资源，不表示启动线程或自动加锁 |
| `lock_guard` | 作用域内持有锁，退出自动解锁 |
| `unique_lock` + wait | 等待时暂时放锁，醒来重新检查条件 |
| `atomic.load/store` | 单个共享值可安全读写，仍需理解业务关系 |
| `= delete` | 明确禁止操作，例如复制连接或移动回调对象 |
| `override` | 编译器核对确实实现了基类虚函数 |
| `final` | 当前类不再允许继续派生 |
| `ClassName::function` | 判断函数所属类，不能仅靠所在目录判断 |
| cpp 匿名命名空间 | 模块内部实现不向其他文件公开 |
